# Работа над компачами Victoria 3

Я поддерживаю набор компатч-модов для Victoria 3 **1.13** (exe сейчас 1.13.11, моды объявляют `1.13.*`). Компач — мини-мод, стыкующий два чужих мода. Цель всегда: **минимальный компач**, чем меньше перекрывает файлов, тем меньше ломается при обновлениях.

Два особых случая со своими разделами ниже: **компач-замена** — когда чужой компач сам нуждается в починке, дешевле не патчить его сверху, а нести его файлы целиком и править нужные на месте. **Мегапак** — все компачи набора, слитые в один мод.

## Папки (всё через `device_bash`, корень `$HOME/mnt`)

**Мои моды (git, сюда пишем):** `Projects/vic3_mods/`

- `_ef/`, `_morg/`, `_pbe/`, `_psc/`, `_tgr/` — компачи по парам модов; `stuff/` — прочее (bpm, mmrpa, tr, vc)
- `сводки по модам/` — по `.md` на каждый чужой мод: что меняет, версия, дата сверки
- `tools/` — скрипты анализа и генераторы; `__megapacks/`, `__translations/`
- Суффиксы папок = статус: `done` / `noneed` (проверено, конфликта нет) / `out` (свежая распаковка чужого мода, источник для генератора) / `out outdate`
- Пары именуются в алфавитном порядке без дублирования: пара `X+Y` лежит в папке первого по алфавиту. Поэтому «все компачи набора» надо собирать обходом всех папок `_*`, а не одной

**Чужие моды (только читать):** `Projects/vic3_mods_out/` — E&F, Morgenrote, PSC, BPM, MMRPA, PowerBlocksExpanded, TechRes+Kuromi, TheGreatRevision, TGR_Loans, _cmf, _etf, плюс `.vanillaVIC3/` (скрытая, `ls -a`) — ваниль, эталон для сравнений.

**Игра:** `mod/` — папка модов Paradox, сюда синхронизируются готовые компачи (писать всегда в оба места, потом `diff -rq`). `logs/` — error.log, game.log, debug.log. `crashes/`, `exceptions/`, `content_load.json`, `launcher-v2.sqlite`.

> Монтируется не всё и не всегда. Если в сессии подключён только `Projects`, `mod/` недоступен — синхронизацию в игровую папку сделать нельзя. Сказать об этом явно и попросить добавить папку, а не молча пропустить шаг.

## Технические правила

- `device_bash` = моя машина, `Bash` = облако. Разные ФС, для модов только `device_bash`
- Удалять нельзя (`rm` → Operation not permitted) → `mv` в `_to_delete/` внутри того же монтирования; `Projects/` и `mod/` — разные монтирования. **`rmdir` запрещён тоже** — после переноса файла пустая папка остаётся. Игре это не мешает, но `diff -rq` репозитория с игровой папкой на ней ругается («Only in ...: <папка>») — это не расхождение
- Мост периодически отваливается, подождать 60–120 сек и повторить
- `grep` с кириллицей падает («Invalid collation character») → искать через `python3`
- **У `device_bash` таймаут 45 сек.** Рекурсивный `os.walk` / `grep -r` по целому моду через монтирование в него не укладывается — сужать путь до конкретной `common/<категория>/`. Полный обход мода делать скриптами из `tools/`, они на это рассчитаны
- Перенос файла из облака на диск: `SendUserFile` → `device_commit_files` с полученным `fileUuid`. Гонять содержимое через base64 в командной строке — дорого и не нужно
- **Кодировки.** В игровых `.txt` / `.yml` BOM нужен там, где в файле есть не-ASCII — `encoding='utf-8-sig'` или `printf '\xEF\xBB\xBF'`. Чистый ASCII работает и без BOM (UTF-8 и Latin-1 на ASCII совпадают), и **побайтовым копиям чужих файлов BOM добавлять нельзя** — ломается дифф против новой версии чужого мода. Поэтому самопроверка ищет не «файл без BOM», а «файл без BOM, в котором есть байт >127 в НЕкомментарной строке». ASCII-арт в шапках чужих файлов под это не попадает и трогать его не надо. В `.metadata/metadata.json` **BOM ЗАПРЕЩЁН**: лаунчер парсит его строгим JSON и падает на `\xEF\xBB\xBF` перед `{` — в списке модов варн «Не удалось обработать метаданные», мод не грузится. Правило: `.json` пишем только `encoding='utf-8'` (никогда `'utf-8-sig'`), после записи проверяем `b[:3] != b'\xEF\xBB\xBF'` и `json.loads`
- После каждой правки — баланс скобок: `s.count('{')-s.count('}')` должен быть 0 (комментарии срезать: `l.split('#')[0]`). Плюс **проверка на дубли top-level ключей по всему моду** — два определения одного ключа в разных файлах мода дают победителя по порядку имён файлов
- **Порядок файлов внутри мода — побайтово по имени, и `_` (0x5F) идёт ПЕРЕД буквами.** Практически: `zz_ef_` < `zz_pb_` < `zz_tr_` < `zzef_` < `zztr_` < `zzz_` < `zzzz_`. Ловушка: `zztr_vanilla_buildings.txt` грузится ПОСЛЕ `zz_tr_kai_tgr_buildings.txt`, а не наоборот, как читается на глаз. В спорном случае сортировку считать (`sorted()`), а не прикидывать

### Python на этих файлах

- **`io.open(path,'w',...)` труncate'ит файл ДО проверки аргументов.** Опечатка в `newline='\\n'` (вместо `'\n'`) → `ValueError: illegal newline value`, а файл уже нулевой длины. Так был обнулён генератор на 2282 строки. Правило: писать во временный файл рядом и `os.replace(tmp, path)`
- Heredoc для python-скриптов только в кавычках (`<<'PY'`), иначе bash съест `$` и backticks
- Многошаговые правки одного файла делать одним скриптом с `assert old in s` на каждый кусок — иначе половина применится, половина упадёт
- Текст с игровым синтаксисом (`\xEF`, `\[`, `\d`) внутри python-скрипта держать в raw-строке, иначе экранирование съедается дважды. И следить, чтобы кавычки-ограничители не встречались внутри самого текста

### git на монтировании

- `.git/index.lock` и `.git/HEAD.lock` остаются после сбоя и не удаляются → `mv` в `.git/_stale/` перед каждой git-командой
- `git checkout -- <file>` падает («unable to unlink old») → восстанавливать через `git show HEAD:<path> > <path>`
- Коммит без `user.name`/`user.email` в конфиге → `git -c user.name=... -c user.email=... commit`, значения брать из `git log -1 --format='%an <%ae>'`
- Backticks в `git commit -m` исполняются bash → сообщение всегда через `-F /tmp/msg.txt` с quoted heredoc
- `warning: unable to unlink .git/objects/**/tmp_obj_*` — безвредно, коммит проходит
- `.gitattributes` конвертирует CRLF→LF при индексации: `git diff --stat` покажет правку в один символ на файле, который я не трогал. Это перенос строк, а не правка

Генераторы (пересобирают мод из чужих источников, руками их вывод не править):

У каждого есть `--check` (разъехалось ли, ничего не пишет, код возврата 1) — годится как хук перед сборкой мегапака.

**Ограничения, о которых надо помнить, а не узнавать заново:**

- `check_megapack_conflicts.py` видит только дубли **внутри** сборки. «Файл сборки перекрывает чужой мод» он не ловит вообще — для этого `scan_conflicts.py --a <сборка> --b <каждый мод набора>`
- Он же считает ключи локализации по всем языкам вместе: один ключ в одиннадцати языках выглядит как одиннадцать дублей. Настоящий дубль — только внутри одной `localization/<язык>/`, проверять отдельным проходом
- 98 «дублей» в `common/company_types` в сборках с E&F — штатная конструкция `ef+psc` (`INJECT:` хотфикса поверх собственной копии списка E&F), а не конфликт. Разобрано в шапке файла
- `--check` у генератора читает папку `<имя> out` со свежей распаковкой чужого компача. **Если её нет, генератор печатает `missing: ...` и выходит с кодом 0** — то есть выглядит как «всё сошлось». Папку `out` после генерации не выбрасывать

## Факты про 1.13 (проверены, экономят часы)

### Загрузка и переопределение

- Префиксы БД: `INJECT:` `TRY_INJECT:` `REPLACE:` `TRY_REPLACE:` `REPLACE_OR_CREATE:` — правильный способ править чужой мод. `INJECT:` в список добавляет, не заменяет
- **`REPLACE:` патчит по перечисленным под-блокам, а не заменяет запись целиком.** `REPLACE:key = { modifier = { ... } }` меняет только `modifier`; текстуры, гейты по законам и всё, чего мод не назвал, остаются от предыдущего слоя. Отсюда работает `REPLACE_OR_CREATE:tgr_loans_button_N = { visible = { always = no } possible = { always = no } }` — кнопка гасится, тело остаётся. И отсюда же не нужен компач на company HQ PM: E&F перечисляет только `building_modifiers`, `state_modifiers` от TGR выживает сам
  > Оговорка: шапка `zzzz_ef_tr_fix_gold_minting.txt` до сих пор утверждает обратное («заменяет запись целиком», со ссылкой на два наблюдения в игре 21.08.2026). Её надо перечитать и привести в порядок. Пока это не сделано — в спорном месте писать `REPLACE:` с ПОЛНЫМ телом: это корректно при любом прочтении
- **`REPLACE:` нужен ровно тогда, когда надо УБРАТЬ строку.** Если только добавляем — `INJECT:`, и это разница между 98 дословными копиями чужих определений (7000 строк на передифф при каждом обновлении) и 98 добавками по четыре строки. Прежде чем писать `REPLACE:`, спросить себя: что именно я отсюда убираю
- **Повторяющиеся ключи внутри одного блока модификаторов складываются.** Поэтому `INJECT:base_values = { country_loan_interest_rate_add = 0 }` НИЧЕГО не сбрасывает: `0 + (-0.2)` это `-0.2`. Так «сброс» чужой базовой ставки займов не работал неизвестно сколько времени, ни строчки в логе. Обнулить чужой модификатор можно двумя способами, и первый лучше:
  1. **перекрыть по пути файл, в котором он лежит** — если там больше ничего нет;
  2. контрвес с обратным знаком — но он верен только при сложении и ровно наоборот при перезаписи
- **Ключ без префикса тоже переопределяет.** Обычное `foo = { }` в моде, загруженном позже, съедает `REPLACE_OR_CREATE:foo` из более раннего. Отсутствие префикса ≠ отсутствие конфликта
- Но для `scripted_effects` / `scripted_triggers` / `script_values` **простой повтор ключа в более позднем файле НЕ переопределяет** — нужен `REPLACE_OR_CREATE:`. Симптом молчаливый: старое определение продолжает работать, новое не зовётся никогда
- **Перекрытие файла по относительному пути — грубейший инструмент, но иногда единственный хирургический.** Если чужой файл содержит ровно одну запись, которую надо убрать, а ключ этой записи общий для нескольких модов (`base_values` инжектят четыре файла), то `REPLACE:` по ключу запинит вклад всех остальных — а перекрытие по пути уносит ровно нужное и ничего больше. Условия: (а) убедиться, что в чужом файле правда больше ничего нет; (б) в шапке `!! MAINTENANCE !!` — перекрытие погасит и всё, что автор допишет в этот файл потом, передиффить при каждом обновлении. Приём уже используется в `stuff/anti_tgr_loans`
- **Локализация не подчиняется порядку загрузки: выигрывает ПЕРВЫЙ файл, определивший ключ.** Единственный способ перебить — файл с тем же именем (перекрытие по пути). Следствие: лишние ключи в своём файле, которые чужой мод определяет сам и грузится раньше, — мёртвый груз, а не конфликт; но чистить их стоит, потому что файл врёт о том, что делает компач
- Аддитивны: `common/on_actions/`, `GLOBAL` в `history/global/`, `BUILDINGS` в `history/buildings/`. `zz_` идёт после `99_`
- **`history/buildings` выполняется РАНЬШЕ `history/global`.** На момент истории зданий законы ещё не активированы — любой гейт `has_law` там ложен. Если нужна привязка к стране на этом этапе, единственное, что есть, — тег
- **Ошибки компиляции и `PostValidate` пишутся в `debug.log`, а не в `error.log`.** Эффект с ними просто не существует, вызовы молча ничего не делают

### Скрипт

- **Отсутствующие `has_game_rule` / script value не дают ошибки в логе.** Ветка с ними просто никогда не срабатывает. Самый тихий класс поломок — ловится только грепом имён по чужому моду
- **`$MACRO$`-аргументы подставляются как текст.** `CB_SIZE = var:foo` синтаксически проходит, но внутри `add_ownership = { company = { levels = $CB_SIZE$ } }` чтение `var:` не резолвится → 0 уровней, ни ошибки, ни лога. Четыре страны остались без центробанка. Передавать литералы; если значение переменное — лестница из литералов по веткам
- **Аргумент, который вызывающие передают, а эффект не использует, — фатальная ошибка компиляции** (`jomini_script_argument.cpp:182`), рушит весь эффект целиком
- `add_modifier { multiplier = X }` считает X **НЕ** в скоупе эффекта — внутри `every_scope_state` любое `state_*` вернёт none. Расчёт должен быть страновым
- **Прежде чем ограничивать чужую величину — выяснить её единицу и рабочий диапазон по тому, куда она подставляется.** У E&F `target_demand_currency_for_modifier` — процент отклонения, и он уходит в `multiplier` модификатора-**mult**: чтобы поднять банк с 27 единиц выпуска до британских 100K, нормальное значение около 370 000. Сотни тысяч там — рабочий режим, а не переполнение. Я трижды подряд «чинил» это потолком (25000 → занижение в пятнадцать раз, 100000 → вчетверо) и guard'ом (страна вообще перестала печатать)
- У рынков нет переменных. Путь до владельца: `market ?= { owner ?= { } }`
- **Итераторы в script value работают ТОЛЬКО скоуповые.** `every_scope_state = { add = 1 }` работает (образец — ванильный `country_total_urbanization`), а глобальные — `every_country` и родня — НЕ выполняются и молча дают 0. Именно потому, что первое работает и задокументировано, второе выглядит правдоподобно. Сумма осталась нулём, `min = 1` сделал её единицей, и доля каждой страны вышла «весь рынок мой»: 1.22M валюты против 214K спроса, цена −98%. Ни строчки в логе — script value, тихо вычислившийся в ноль, неотличим от того, который в ноль вычислился законно. Правило: **любую сумму по списку считать в эффекте и класть в переменную**, script value оставить деление
- Вход в товар: `mg:X` в рынке, `sg:X` в штате
- **Пульсы размазаны по дням.** `on_monthly_pulse_country` пересчитывает ~1/30 стран каждый день, `ef_on_yearly_pulse_country` — ~1/365. У каждой страны свой день, и он повторяется: Бенгалия 1 января два года подряд, Китай в апреле. Диагностический признак: **«скачет у всех, но в разные месяцы» = годовой пульс, а не случайность**. Обратная сторона — если значение считает каждый сам, на рынке из шести стран будет шесть слегка разных копий одного числа
- **У рынков нет переменных, но есть владелец.** Одно число на рынок хранить у `market.owner` и читать `market.owner.var:X` — тогда все участники читают одну копию
- `is_building_group` идёт по цепочке родителей — часто из-за этого патч не нужен вообще
- **`log = "..."` в 1.13 никуда не пишет** — ни в game.log (там только ошибки скриптов), ни в error.log. Отладочный вывод через него бесполезен, диагностику строить на наблюдаемых последствиях
- Предпочитать конструкции, которые уже подтверждены в этом же коде. Если чужой мод свою версию закомментировал (`any_company = { is_company_type = ... }` у E&F) — это причина ей не доверять; `has_company = company_type:X` работает точно
- Ошибок в `error.log` может не быть ни на что из перечисленного. Молчание — не подтверждение

### Компании, здания, товары

- **`building_types` у компании — единственный настоящий замок на то, кто может владеть зданием.** Монополия — правило цены и строительства, а не замок: чужая компания с этим типом в списке спокойно приватизирует здание у монополиста
- **`add_ownership` существует только внутри `create_building`.** Эффекта «передать стоящее здание компании» в игре нет — ни в `effects_l_english.yml`, ни в `common/effect_localization/`. Значит здание должно рождаться уже во владении, а «передать» = снести и построить заново
- **`level` не может стоять рядом с `add_ownership`** в одном `create_building`: `PostValidate ... returned false`, блок выбрасывается целиком. Уровень = сумма `levels` во владениях. В ванили 3128 блоков с `add_ownership` и ни одного с `level`
- Расширение существующего здания отдаёт НОВЫЕ уровни государству — `add_ownership` покрывает только уровни, созданные вместе со зданием. **Осторожно: это наблюдение сделано на чужом вызове БЕЗ `add_ownership`** и не проверено для вызова с ним. Так родилось «сносить и строить заново», а у сноса своя цена (ниже)
- **Пересоздание здания стоит месяц простоя и уносит всё, что висело на здании.** Новое здание набирает рабочих, а модификаторы, навешенные на постройку (у E&F — `currency_demande`, множитель эмиссии), исчезают вместе с ней. После пересоздания надо заново звать ВСЕ чужие setup-эффекты, а не только тот, что выставляет производственные методы. Симптом был красивый: у быстрорастущих стран раз в год цена валюты падала в пол — спавнер зовётся на годовом пульсе с размером, растущим от `gdp_view`, страна раз в год пересекала порог, и банк перестраивался
- **Похожие имена `building_group` у двух модов — это РАЗНЫЕ группы.** T&R `bg_heavy_industry` и TGR `bg_industry_heavy` — не опечатка и не синоним: у TGR это дети `bg_manufacturing`, и на них завязаны его промышленный декрет, законы экономических стимулов и `building_group_*` модификаторы; группа T&R им сестра, `is_building_group` до неё не дотягивается. Мердж, потерявший одну строку `building_group`, молча выкидывает здание из половины механик чужого мода. Ни строчки в логе: триггер не сломан, он отвечает «нет»
- **`has_max_level = yes` + `state_building_<тип>_max_level_add`** — ванильная пара. У `building_construction_sector` она есть в ванили (техи дают +10/+5/+5/+5/+5), у `building_trade_center` тоже; TGR обе просто переносит из ванили. Мод, который `REPLACE:`-ит такое здание и не упоминает `has_max_level` (так делает PSC), либо снимает потолок, либо наследует его — в зависимости от того, как читать `REPLACE:`. Симптом, если наследовал не то, однозначный: здание не растёт выше 1 уровня
- **Максимум 3 престижных товара на базовый товар.** Реальными слотами становятся только первые три объявления, всё дальше молча падает в третий. Дефайна нет, число в exe
- `possible` у престижного товара вычисляется в скоупе страны
- `flavored_company = yes` блокирует динамические имена (все 10 ванильных шаблонов несут `use_for_flavored_companies = no`) — и тогда именем становится ключ локализации типа компании. Это рабочий способ дать компании фиксированное имя
- Динамическое имя вставляет `$DYNAMIC_NAME_TAG$` в СЕРЕДИНУ шаблона (`[Adjective] $TAG$ $TYPE_NAME$`), а не подписывает снизу. Отсутствующий ключ виден игроку как `ZZ_..._DYNAMIC_NAME_TAG_SINGULAR` посреди названия
- **`ownership_type` (у здания) и `is_government_funded` (у building group) — разные переключатели.** Первый даёт доли для компании, второй определяет, платит ли казна за входы и забирает ли выпуск. Пока второй включён, панель честно называет здание правительственным, даже если компания на вкладке владения есть, и компания не получает с него ничего. Это может быть намеренно
- Потолок **128 товаров**. 130+ = вылет при входе в игру, без единой ошибки в логе. Закомментированные не считаются. Ваниль = 53
- **Товары считать по виртуальной ФС, а не суммой по модам.** Порядок: пройти моды в порядке загрузки, собрать словарь `common/goods/<имя файла>` → мод (поздний перекрывает ранний по пути), потом посчитать ключи, которые в получившемся наборе создаются впервые (без префикса или `REPLACE_OR_CREATE:`); `REPLACE:` / `INJECT:` ванильных не считаются. Иначе цифра врёт втрое: E&F в одиночку даёт +73, но хотфикс перекрывает `common/goods/ef_00_goods.txt` целиком и остаётся +8. Текущий полный набор из шести модов = **106 из 128**
- `normal_modifier_time = 1825`, и ваниль скармливает его `days`. Если чужой мод пишет `months = normal_modifier_time` — это 152 года, то есть навсегда. В мердже такие места брать у того мода, где стоит литерал
- В `modifier_type_definitions` поля `decimals`, `color`, `percent` — **только отображение**. Расхождение по ним между модами конфликтом не является, пин-файл писать не надо
- Варн лаунчера «Не удалось обработать метаданные» = `metadata.json` не разобрался, при этом сам JSON может быть валидным. Порядок проверки: BOM (самая частая причина) → `json.loads` → набор ключей. Быстрая диагностика — прогнать разом все `metadata.json` игровой папки и сравнить проблемные с рабочими. Лишние ключи внутри `game_custom_data` (`tested_with`) лаунчер терпит
- GUI: движок ищет виджеты по имени. Устаревшая копия ванильного `.gui` без виджета = вылет, а не лог. Признак: в диффе «минус сотни строк, плюс две-три». Проверка мерджа `.gui`: множество имён виджетов в файле компача должно быть **надмножеством** обоих модов, чьи версии мерджили; расхождение с ванилью само по себе не улика — важно, выпилил ли строку хоть один из авторов
- **`.gui` умеет прятать целые сущности по имени, и в `common/` этого не видно.** У E&F в `building_details_panel.gui` одна строка `visible` собрана из двенадцати `EqualTo_string(ProductionMethodGroup.GetKey,'pmg_X')` — и группа «какую валюту печатает банк» просто не рисуется. Я проверил по очереди `unlocking_laws`, состав группы, список законов, все 97 текстур и флаг `is_hidden_when_unavailable` — всё корректно, потому что ответа в `common/` не было вовсе. Правило: **если виджета нет, а данные в порядке — грепать имя сущности по `gui/`**

## Диагностика

Порядок, который реально экономит раунды. Первые семь пунктов — про вылет, дальше — про «работает, но неправильно», что оказалось дороже вылетов.

1. **`crashes/` — сначала туда, а не в логи.** В `crashes/<дата>/exception.txt` тип исключения и стек. `EXCEPTION_STACK_OVERFLOW` = рекурсия или слишком глубокая вложенность; `EXCEPTION_ACCESS_VIOLATION` = обычно что-то другое. Рядом лежит снимок `logs/` на момент падения — он полезнее текущего.
2. **Считать кадры стека:** `grep -c victoria3.exe exception.txt`. Число, упирающееся в одно и то же значение (4182 / 4187) при совершенно разных правках, означает **бесконечную рекурсию**, а не длинную цепочку: глубину задаёт лимит стека, а не скрипт. Сравнить с крэшами прошлых дней в той же папке — если картина не менялась от всех правок, причина не в них.
3. **Сводка логов вместо чтения подряд:** `sed -E 's/^\[[0-9:]+\]//' error.log | sed -E 's/[0-9]+/N/g' | sort | uniq -c | sort -rn | head -40`. Спам в 12 тысяч строк вытесняет из буфера всё остальное — сводка это показывает мгновенно.
4. **`content_load.json`** — что было включено в последнем запуске, включая пути (workshop или локальная папка).
5. **`launcher-v2.sqlite`** — полная картина плейсета. Скопировать в `/tmp` и читать:
   ```sql
   select m.displayName, m.dirPath, pm.enabled, pm.position
     from playsets_mods pm join mods m on m.id = pm.modId
    where pm.playsetId = (select id from playsets where isActive = 1)
    order by pm.position
   ```
   Здесь видно то, что иначе не видно никак: **один и тот же мод стоит дважды — из мастерской и из локальной `mod/`, и включена не та копия**; нужный компач выключен; порядок загрузки не тот, что требует README. В сессии это оказалось причиной вылета, которую я до того искал в скриптах.
6. **Циклы в чужих эффектах.** Построить граф вызовов по `scripted_effects` обоих модов и найти циклы. Если цикл есть только у чужого мода и не задевает моих ключей — это не моё, и надо сказать это прямо, а не «починить» наугад.
7. Правку своих файлов начинать, только когда пункты 1–6 сузили место. Иначе получается ремонт того, что не ломалось.

### Когда ничего не падает, но числа странные

8. **Просить список стран, у кого проявляется, и у кого нет.** Это самый дешёвый и самый информативный запрос. «У Нидерландов и Германии по два ЦБ и тихо, у Франции один и скачет» за одну реплику убило гипотезу про число эмитентов и вывело на скорость роста экономики. Мои гипотезы дважды подряд были правдоподобны и неверны — список стран не был.
9. **Считать арифметику прямо по скриншоту.** 1.22M производства против 214K спроса — это примерно число центробанков на рынке, то есть «каждый берёт весь рынок себе», а не «формула шумит». Экран с рынком даёт производство, потребление, цену и разбивку по странам; этого хватает, чтобы отличить перепроизводство в N раз от колебания.
10. **Периодичность — это подпись механизма.** Ровно раз в год у каждого свой месяц = годовой пульс. Раз в месяц, но у всех в разные дни = месячный. «В случайный момент» почти никогда не случайно.
11. **Читать собственные шапки сгенерированных файлов и старые коммиты.** Ответ про пропавшую строку в панели банка лежал в комментарии моего же генератора, тремя строками выше того места, которое я в тот момент правил.
12. **Проверить, что «сброс» вообще что-то сбрасывает.** Строка вида «здесь мы возвращаем значение в 0» — это утверждение, а не факт. У модификаторов ключи складываются, у локализации выигрывает первый файл, у `scripted_effects` повтор не переопределяет. Каждый такой файл проверять по правилу той категории, в которой он лежит, а не по тому, что написано в его собственной шапке.

## Анализ 2: нужен ли компач вообще

`noneed` — половина папок, и это правильный результат.

- `scan_conflicts.py --a --b`. Пусто → компач не нужен, помечать `noneed`, конец
- Пересечение по путям файлов → смотреть порядок загрузки и теряется ли содержательное. Часто оба мода делают `TRY_INJECT` в один ванильный файл — конфликта нет

Иначе в мегапаке тот же ключ всплывёт снова, и придётся выяснять заново, конфликт это или воспроизведение того же исхода

## Компач-замена

Когда чужой компач сам сломан и правок к нему набирается больше двух-трёх, дешевле сделать самостоятельный мод, который его заменяет, чем слой поверх.

- **Почему.** Слой требует, чтобы чужой компач был включён, стоял раньше и не менял форму. Любое из трёх нарушено — и `INJECT:` ложится на ключи, которых нет. Плюс сверху можно только добавить правильный ключ, а битый чужой остаётся и продолжает логировать
- **Как.** Свежую распаковку чужого компача класть в `_ef/<имя> out`. Генератор копирует все его файлы **байт в байт**, кроме тех, что правит; правленые пишутся **под их же именами**, чтобы ключ нигде не определялся дважды
- **Своей шапки на скопированные файлы не ставить** и **BOM им не добавлять** — именно чтобы дифф против новой версии чужого компача остался побайтовым
- Битые чужие ключи теперь чинятся на месте (список замен в константе генератора), а обходные блоки из своих файлов убираются — иначе группа инжектится дважды
- В `metadata.json` и README сказать прямо: **запускать ВМЕСТО чужого компача, не вместе с ним**. Иначе каждый ключ определён дважды и побеждает случайный
- Старые файлы-слои удалить из мода (через `mv` в `_to_delete/`), иначе они переопределят то, что теперь лежит в чужих файлах

## Сборка мегапака

Мегапак — все компачи набора, слитые в один мод, чтобы не включать восемь галочек. Лежит в `__megapacks/<имя>/`. **Состав: все пары модов набора, кроме помеченных `noneed`.** Для набора из шести модов это восемь компачей, а не пятнадцать. Варианты сборки («no tgr», «no t&r») отличаются только тем, какие пары из состава выпадают.

### Порядок работы

- **Собирать из компачей, а не править предыдущую сборку.** Старая сборка отстаёт на все переименования файлов, случившиеся в компачах с прошлого раза, и в ней уже не отличить «файл переименовали» от «файл удалили». Правильный цикл: составить целевой список файлов из текущих компачей → всё, чего в нём нет, `mv` в `_to_delete/<имя>_rebuild_<дата>/` → скопировать целевое поверх
- **Ближайшая готовая сборка — хорошая база.** «Сборка из шести модов» = «уже проверенная сборка из пяти» + компачи шестого. Но покрытие всё равно пересчитать целиком
- **Проверка покрытия — обязательный шаг, не формальность.** Скрипт: для каждого компача сверить каждый его файл со сборкой побайтово (`filecmp.cmp`). На выходе три числа на компач: сколько файлов, сколько отсутствует, сколько отличается. **Любое ненулевое значение обязано иметь письменное объяснение** — иначе это не сборка, а то, что от неё осталось. Законные отклонения бывают трёх видов: файл компача заменён в сборке мердж-версией; файл компача в сборке не нужен (его работу делает другой компач); megapack-only файл, которого нет ни в одном компаче
- В конце — тот же прогон в игровую папку и `diff -rq`. Пустые папки после `mv` в диффе — не расхождение

### Что ловить

- **Типовой конфликт мегапака: два компача `REPLACE:` одну и ту же запись, каждый ради своей строки.** По отдельности оба правы; вместе побеждает тот, чьё имя файла позже, и строка другого пропадает молча. За одну сессию таких нашлось три: PMG у `building_manzoni_publishing_industry`, `building_group` у автомобильной промышленности и завода синтетики, две строки модификатора в `malaria_prevention`. Лечится файлом `zzzz_megapack_<про что>.txt`, который грузится последним и несёт объединённое тело
- **Конфликт «сборка перекрывает чужой мод» внутренним чеком не ловится.** Обязательно `scan_conflicts.py --a <сборка> --b <каждый мод набора>` плюс отдельная проверка пересечений **по путям файлов**. Список пересечений должен быть ровно тем, который ожидался (мердж `.gui`, генерируемые копии) — любое лишнее имя разбирать
- **Товары считать заново на всей цепочке** (см. правило про виртуальную ФС). Добавление мода, который «своих товаров не добавляет», всё равно повод пересчитать
- **Локализация: проверять по каждой языковой папке отдельно**, иначе одиннадцать языков читаются как одиннадцать дублей

### Megapack-only файлы

- Имя `zzzz_megapack_<про что>.txt` — чтобы грузиться после всего остального
- **Шапка обязана начинаться со строки «этого файла нет ни в одном компаче»** и дальше отвечать: какие файлы конфликтуют и в каком порядке грузятся, что именно теряется, как это выглядит в игре (обычно никак — так и написать, что симптом молчаливый). Плюс `!! MAINTENANCE !!`: из какого файла выведено тело и что перевыводить после обновления чужого мода
- Тело выводить **из того файла, который сейчас побеждает**, заменив в нём ровно недостающие строки, — а не писать заново. Так дифф против следующей версии остаётся читаемым
- Если тело выведено из генерируемого файла (`zztr_vanilla_buildings.txt`), сказать об этом прямо: тот файл перегенерируется, этот нет

### Метаданные и README сборки

- `relationships` перечисляют **все** моды набора, включая обязательные довески (E&F Hotfix), которых в самой сборке нет
- В README — порядок загрузки со всеми ними и **явная строка, почему сборка грузится после хотфикса** (она несёт свою копию списка компаний и переприменяет поверх неё то, что хотфикс инжектит; в обратном порядке хотфикс инжектит не туда)
- Раздел «что делает только эта сборка» — по строке на каждый megapack-only файл, человеческим языком
- Версия: свой счётчик сборки, `supported_game_version` = `1.13.*`, `tested_with` со всеми версиями и датами

## Генераторы

Всё, что переписывает чужой мод, должно быть скриптом в `tools/`, а не ручной правкой. Правила, оплаченные раундами тестов:

- **Источник истины брать из самого чужого мода, а не из своей таблицы.** Ручной список «тег → сущность» проигрывает гонку с чужим ростером: таблица называла для Китая Da-Qing Bank (основан в 1905), а страна держит Imperial Bank of China — и так для четырёх стран. У E&F список банковских компаний лежит в `private_bank_type` в `customizable_localization`. Своя таблица допустима только для приоритета, не для членства
- Прочитанный список сверять с реально существующими ключами: у E&F в его же перечне написано `company_BankSBoBS`, а компания называется `company_BankSBoBSA`. `REPLACE:` несуществующего ключа — ошибка загрузки
- **Следить за префиксом при склейке.** `top_block()` возвращает блок ВМЕСТЕ с `REPLACE:`; ещё один прибавленный сверху даёт `REPLACE:REPLACE:building_x`, и запись молча не грузится
- Длинные `if/else_if` цепочки не строить: цепочка вкладывается, 145 веток = 145 кадров стека. Плоские `if` с флагом-переменной ведут себя так же (first-match-wins), а глубина остаётся единицей. Само по себе это не всегда причина вылета — но проверять такое дорого, а писать плоско ничего не стоит
- Генератор печатает, что именно он поправил в этот прогон, и это уходит в шапку файла. Пустой список или новый пункт = источник изменился, надо прочитать
- Самопроверка в конце прогона: баланс скобок, кодировка, дубли ключей
- Удаление своего же устаревшего вывода делать через `try/except OSError` с внятным «DELETE ME» — мост не умеет unlink, и падать из-за этого весь прогон не должен
- **Папку `<имя> out` не выбрасывать.** `--check` читает именно её, и без неё выходит с кодом 0 — то есть врёт про «всё сошлось»

## Чего не делать

- Не «чинить» замысел автора, не разобравшись. Страна без банка может быть гейтом за игровым событием, а не багом. Сначала найти, кто и при каких условиях выдаёт нужное
- **Не удалять файл, приняв его за мусор, пока не проверено, что он не половина работающего механизма.** `zz_ef_cm_bank_group.txt` выглядел остатком эксперимента с флагом; на деле он был второй половиной владения центробанком, и его удаление вернуло «правительственное» здание. Если файл закоммичен и лежал в рабочей сборке — у него была причина
- Не восстанавливать ванильные проверки, которые **оба** мода выпилили независимо друг от друга: это компач придумывает поведение, которого не хочет ни один автор. Это же правило — ответ на «в мердже `.gui` не хватает трёх ванильных виджетов»: если их выпилили оба автора, восстанавливать нечего
- Не изобретать формулу, если данные есть в моде — потребности попов в `common/buy_packages/`, цены в `common/goods/`
- Не строить обратную связь от рынка — «подгонять выпуск под потребление» самораскручивается
- **Делитель, который механизм сам и производит, нельзя защищать через `if делитель > 0`.** Получается замкнутый круг: чтобы начать печатать, надо уже печатать. Зажимать снизу (`divide = { value = X min = 1 }`), как это делает сам автор в соседнем блоке. Тот же guard у соседних товаров корректен — там делитель растёт сам по себе, это разные по природе величины
- **Не обнулять чужой модификатор нулём.** `INJECT:` в блок модификаторов складывает: `0` не сбрасывает `-0.2`. Убирать либо перекрытием файла по пути, либо контрвесом — и в комментарии сказать, почему выбран именно этот способ
- **Не добавлять BOM в побайтовые копии чужих файлов.** Правило «BOM обязателен» — про свои файлы с не-ASCII содержимым. Копия чужого компача должна остаться побайтовой, иначе ломается дифф против его новой версии. Проверять надо не «есть ли BOM», а «есть ли не-ASCII в некомментарной строке файла без BOM»
- Не доверять чужому анализу без проверки — присланный разбор от другой модели был неверен в 4 пунктах из 7. Своей прошлой сводке, своему прошлому README и шапке своего собственного файла — тоже. Если две мои записи об одном и том же противоречат друг другу, это надо назвать вслух и разрешить, а не молча выбрать удобную
- Не осторожничать с восстановлением `.gui` — разбирать дифф построчно, а не по объёму
- Не оставлять правку в одном месте — репозиторий, игровая папка и **все** мегапаки должны совпадать всегда. Список копий получать грепом по имени файла, а не по памяти
- **Не чинить симптом, не поняв, симптом чего это.** Здание, которое числится правительственным при живом владельце-компании, выглядит багом; «починка» перевела прибыль центробанка компании и была откачена. Прежде чем менять поведение, отделить «panel врёт» от «panel честно показывает то, что происходит с деньгами»
- **Не «чинить» число, не поняв, что оно означает.** Три подряд неверные починки одного симптома вышли из того, что я принял множитель за объём. Сначала вычислить, куда величина подставляется и какой у неё нормальный диапазон, потом трогать
- **Ограничение — это не починка.** Просьба «почини формулу, чтобы не скакала» не выполняется потолком: потолок прячет симптом и ломает рабочий режим. Искать, что именно делает вход неверным
- **Не гадать больше двух раз подряд.** Если две гипотезы не подтвердились, идти за фактами: crashes, sqlite плейсета, граф вызовов. Признавать «это не моё» — нормальный результат
- **Спрашивать перед архитектурной развилкой.** 95 типов компаний → 1 стоило одного вопроса и сняло три класса багов разом. Развилка «сделать проще, но иначе» — это вопрос к пользователю, а не решение в тишине. Но сначала проверить, развилка ли это: «сборка перекрывает конструкцию TGR» оказалось воспроизведением того же исхода, который получается и без сборки, — спрашивать было не о чем

## Формат результата

Комментарии в коде и README — на английском, общение со мной — на русском. README компача — стимовский BBCode, компактно; для больших модов подробный markdown + отдельный раздел `## For Steam` с коротким BBCode-блоком. Комментарий должен отвечать «почему так, а не иначе», а не пересказывать код — особенно там, где уже наступали на грабли, с цитатой ошибки из лога (а если ошибки в логе не бывает — так и написать, что симптом молчаливый, и какой именно).

Сообщение коммита — в том же жанре: что было сломано, как это выглядело со стороны игры, почему выбрано это решение. Ревертящий коммит обязан объяснить, почему предыдущий был неправ.

Письмо автору чужого мода — на английском, по-коллегиальному, без поучений: что я сделал и как это устроено → цифры → **список найденных багов в его моде** (для него это самое ценное) → ссылка на репозиторий с «берите что нужно». Каждый баг одной фразой: где, что не так, как проявляется. Свои решения подавать как «вот что вышло», а не как «вам надо сделать так».

Разбор конфликтов класть рядом с компачем отдельным `.md` (`conflicts_<a>_vs_<b>_report.md`): вывод `scan_conflicts.py` + раздел «почему это не конфликт / почему мерджим», таблицей «ваниль vs мод A vs мод B» по спорной записи. Статус пары дублировать строкой в таблицу «Статус пар» в сводке по каждому из двух модов.

Для сборки — `conflicts_megapack[_<вариант>]_internal.md` в корне сборки: машинный вывод `check_megapack_conflicts.py`, а под ним раздел разбора из четырёх частей: **«требуют работы — сделано»** (по группе на каждый megapack-only файл, с порядком загрузки и симптомом), **«не конфликты»** таблицей «группа → почему», **«пересечения сборки с самими модами»** (вывод `scan_conflicts.py` против каждого мода набора, и что из этого намеренно), **«проверки сборки»** — числа: файлов, баланс скобок, кодировки, дубли локализации по языкам, товары против 128, покрытие компачей с перечислением всех законных отклонений.

Открытые вопросы, которые не удалось закрыть в этой сессии, писать отдельным разделом с явной пометкой, на что они влияют, а на что нет. Вопрос, ответ на который ничего не меняет в текущей работе, — не повод останавливаться, но и не повод молчать.
