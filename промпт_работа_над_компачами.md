# Работа над компачами Victoria 3

Я поддерживаю набор компатч-модов для Victoria 3 **1.13** (exe сейчас 1.13.11, моды объявляют `1.13.*`). Компач — мини-мод, стыкующий два чужих мода. Цель всегда: **минимальный компач**, чем меньше перекрывает файлов, тем меньше ломается при обновлениях.

Отдельный случай — **компач-замена**: когда чужой компач сам нуждается в починке, дешевле не патчить его сверху, а нести его файлы целиком и править нужные на месте. См. раздел «Компач-замена».

## Папки (всё через `device_bash`, корень `$HOME/mnt`)

**Мои моды (git, сюда пишем):** `Projects/vic3_mods/`

- `_ef/`, `_morg/`, `_pbe/`, `_psc/`, `_tgr/` — компачи по парам модов; `stuff/` — прочее (bpm, mmrpa, tr, vc)
- `сводки по модам/` — по `.md` на каждый чужой мод: что меняет, версия, дата сверки
- `tools/` — скрипты анализа и генераторы; `__megapacks/`, `__translations/`
- Суффиксы папок = статус: `done` / `noneed` (проверено, конфликта нет) / `out` (свежая распаковка чужого мода, источник для генератора) / `out outdate`

**Чужие моды (только читать):** `Projects/vic3_mods_out/` — E&F, Morgenrote, PSC, BPM, MMRPA, PowerBlocksExpanded, TechRes+Kuromi, TheGreatRevision, TGR_Loans, _cmf, _etf, плюс `.vanillaVIC3/` (скрытая, `ls -a`) — ваниль, эталон для сравнений.

**Игра:** `mod/` — папка модов Paradox, сюда синхронизируются готовые компачи (писать всегда в оба места, потом `diff -rq`). `logs/` — error.log, game.log, debug.log. `crashes/`, `exceptions/`, `content_load.json`, `launcher-v2.sqlite`.

> Монтируется не всё и не всегда. Если в сессии подключён только `Projects`, `mod/` недоступен — синхронизацию в игровую папку сделать нельзя. Сказать об этом явно и попросить добавить папку, а не молча пропустить шаг.

## Технические правила

- `device_bash` = моя машина, `Bash` = облако. Разные ФС, для модов только `device_bash`
- Удалять нельзя (`rm` → Operation not permitted) → `mv` в `_to_delete/` внутри того же монтирования; `Projects/` и `mod/` — разные монтирования. **`rmdir` запрещён тоже** — после переноса файла пустая папка остаётся, игре это не мешает
- Мост периодически отваливается, подождать 60–120 сек и повторить
- `grep` с кириллицей падает («Invalid collation character») → искать через `python3`
- **У `device_bash` таймаут 45 сек.** Рекурсивный `os.walk` / `grep -r` по целому моду через монтирование в него не укладывается — сужать путь до конкретной `common/<категория>/`. Полный обход мода делать скриптами из `tools/`, они на это рассчитаны
- Перенос файла из облака на диск: `SendUserFile` → `device_commit_files` с полученным `fileUuid`. Гонять содержимое через base64 в командной строке — дорого и не нужно
- Кодировки: в игровых `.txt` (локализация, скрипты) **BOM обязателен** — `encoding='utf-8-sig'` или `printf '\xEF\xBB\xBF'`. В `.metadata/metadata.json` **BOM ЗАПРЕЩЁН**: лаунчер парсит его строгим JSON и падает на `\xEF\xBB\xBF` перед `{` — в списке модов варн «Не удалось обработать метаданные», мод не грузится. Правило: `.json` пишем только `encoding='utf-8'` (никогда `'utf-8-sig'`), после записи проверяем `b[:3] != b'\xEF\xBB\xBF'` и `json.loads`
- После каждой правки — баланс скобок: `s.count('{')-s.count('}')` должен быть 0 (комментарии срезать: `l.split('#')[0]`). Плюс **проверка на дубли top-level ключей по всему моду** — два определения одного ключа в разных файлах мода дают случайного победителя по алфавиту имён файлов
- Порядок файлов **внутри** мода — по имени. `zzzz_` грузится после `zef_`, поэтому `INJECT:` из своего файла ложится на определение из своего же файла

### Python на этих файлах

- **`io.open(path,'w',...)` труncate'ит файл ДО проверки аргументов.** Опечатка в `newline='\\n'` (вместо `'\n'`) → `ValueError: illegal newline value`, а файл уже нулевой длины. Так был обнулён генератор на 2282 строки. Правило: писать во временный файл рядом и `os.replace(tmp, path)`
- Heredoc для python-скриптов только в кавычках (`<<'PY'`), иначе bash съест `$` и backticks
- Многошаговые правки одного файла делать одним скриптом с `assert old in s` на каждый кусок — иначе половина применится, половина упадёт

### git на монтировании

- `.git/index.lock` и `.git/HEAD.lock` остаются после сбоя и не удаляются → `mv` в `.git/_stale/` перед каждой git-командой
- `git checkout -- <file>` падает («unable to unlink old») → восстанавливать через `git show HEAD:<path> > <path>`
- Коммит без `user.name`/`user.email` в конфиге → `git -c user.name=... -c user.email=... commit`, значения брать из `git log -1 --format='%an <%ae>'`
- Backticks в `git commit -m` исполняются bash → сообщение всегда через `-F /tmp/msg.txt` с quoted heredoc
- `warning: unable to unlink .git/objects/**/tmp_obj_*` — безвредно, коммит проходит

## Факты про 1.13 (проверены, экономят часы)

### Загрузка и переопределение

- Файл перекрывается по относительному пути целиком — грубейший инструмент, только в крайнем случае
- Префиксы БД: `INJECT:` `TRY_INJECT:` `REPLACE:` `TRY_REPLACE:` `REPLACE_OR_CREATE:` — правильный способ править чужой мод. `INJECT:` в список добавляет, не заменяет
- **`REPLACE:` нужен ровно тогда, когда надо УБРАТЬ строку.** Если только добавляем — `INJECT:`, и это разница между 98 дословными копиями чужих определений (7000 строк на передифф при каждом обновлении) и 98 добавками по четыре строки. Прежде чем писать `REPLACE:`, спросить себя: что именно я отсюда убираю
- **Ключ без префикса тоже переопределяет.** Обычное `foo = { }` в моде, загруженном позже, съедает `REPLACE_OR_CREATE:foo` из более раннего. Отсутствие префикса ≠ отсутствие конфликта
- Но для `scripted_effects` / `scripted_triggers` / `script_values` **простой повтор ключа в более позднем файле НЕ переопределяет** — нужен `REPLACE_OR_CREATE:`. Симптом молчаливый: старое определение продолжает работать, новое не зовётся никогда
- **Локализация не подчиняется порядку загрузки: выигрывает ПЕРВЫЙ файл, определивший ключ.** Единственный способ перебить — файл с тем же именем (перекрытие по пути)
- Аддитивны: `common/on_actions/`, `GLOBAL` в `history/global/`, `BUILDINGS` в `history/buildings/`. `zz_` идёт после `99_`
- **`history/buildings` выполняется РАНЬШЕ `history/global`.** На момент истории зданий законы ещё не активированы — любой гейт `has_law` там ложен. Если нужна привязка к стране на этом этапе, единственное, что есть, — тег
- **Ошибки компиляции и `PostValidate` пишутся в `debug.log`, а не в `error.log`.** Эффект с ними просто не существует, вызовы молча ничего не делают

### Скрипт

- **Отсутствующие `has_game_rule` / script value не дают ошибки в логе.** Ветка с ними просто никогда не срабатывает. Самый тихий класс поломок — ловится только грепом имён по чужому моду
- **`$MACRO$`-аргументы подставляются как текст.** `CB_SIZE = var:foo` синтаксически проходит, но внутри `add_ownership = { company = { levels = $CB_SIZE$ } }` чтение `var:` не резолвится → 0 уровней, ни ошибки, ни лога. Четыре страны остались без центробанка. Передавать литералы; если значение переменное — лестница из литералов по веткам
- **Аргумент, который вызывающие передают, а эффект не использует, — фатальная ошибка компиляции** (`jomini_script_argument.cpp:182`), рушит весь эффект целиком
- `add_modifier { multiplier = X }` считает X **НЕ** в скоупе эффекта — внутри `every_scope_state` любое `state_*` вернёт none. Расчёт должен быть страновым
- У рынков нет переменных. Путь до владельца: `market ?= { owner ?= { } }`
- Итераторы в script value работают: `every_scope_state = { add = 1 }` (образец — ванильный `country_total_urbanization`)
- Вход в товар: `mg:X` в рынке, `sg:X` в штате
- `is_building_group` идёт по цепочке родителей — часто из-за этого патч не нужен вообще
- **`log = "..."` в 1.13 никуда не пишет** — ни в game.log (там только ошибки скриптов), ни в error.log. Отладочный вывод через него бесполезен, диагностику строить на наблюдаемых последствиях
- Предпочитать конструкции, которые уже подтверждены в этом же коде. Если чужой мод свою версию закомментировал (`any_company = { is_company_type = ... }` у E&F) — это причина ей не доверять; `has_company = company_type:X` работает точно
- Ошибок в `error.log` может не быть ни на что из перечисленного. Молчание — не подтверждение

### Компании, здания, товары

- **`building_types` у компании — единственный настоящий замок на то, кто может владеть зданием.** Монополия — правило цены и строительства, а не замок: чужая компания с этим типом в списке спокойно приватизирует здание у монополиста
- **`add_ownership` существует только внутри `create_building`.** Эффекта «передать стоящее здание компании» в игре нет — ни в `effects_l_english.yml`, ни в `common/effect_localization/`. Значит здание должно рождаться уже во владении, а «передать» = снести и построить заново
- **`level` не может стоять рядом с `add_ownership`** в одном `create_building`: `PostValidate ... returned false`, блок выбрасывается целиком. Уровень = сумма `levels` во владениях. В ванили 3128 блоков с `add_ownership` и ни одного с `level`
- Расширение существующего здания отдаёт НОВЫЕ уровни государству — `add_ownership` покрывает только уровни, созданные вместе со зданием
- **Максимум 3 престижных товара на базовый товар.** Реальными слотами становятся только первые три объявления, всё дальше молча падает в третий. Дефайна нет, число в exe
- `possible` у престижного товара вычисляется в скоупе страны
- `flavored_company = yes` блокирует динамические имена (все 10 ванильных шаблонов несут `use_for_flavored_companies = no`) — и тогда именем становится ключ локализации типа компании. Это рабочий способ дать компании фиксированное имя
- Динамическое имя вставляет `$DYNAMIC_NAME_TAG$` в СЕРЕДИНУ шаблона (`[Adjective] $TAG$ $TYPE_NAME$`), а не подписывает снизу. Отсутствующий ключ виден игроку как `ZZ_..._DYNAMIC_NAME_TAG_SINGULAR` посреди названия
- **`ownership_type` (у здания) и `is_government_funded` (у building group) — разные переключатели.** Первый даёт доли для компании, второй определяет, платит ли казна за входы и забирает ли выпуск. Пока второй включён, панель честно называет здание правительственным, даже если компания на вкладке владения есть, и компания не получает с него ничего. Это может быть намеренно
- Потолок **128 товаров**. 130+ = вылет при входе в игру, без единой ошибки в логе. Закомментированные не считаются. Ваниль = 53. Считать по `common/goods/**`, отличая новые ключи от `INJECT:`/`REPLACE:` ванильных
- `normal_modifier_time = 1825`, и ваниль скармливает его `days`. Если чужой мод пишет `months = normal_modifier_time` — это 152 года, то есть навсегда. В мердже такие места брать у того мода, где стоит литерал
- В `modifier_type_definitions` поля `decimals`, `color`, `percent` — **только отображение**. Расхождение по ним между модами конфликтом не является, пин-файл писать не надо
- Варн лаунчера «Не удалось обработать метаданные» = `metadata.json` не разобрался, при этом сам JSON может быть валидным. Порядок проверки: BOM (самая частая причина) → `json.loads` → набор ключей. Быстрая диагностика — прогнать разом все `metadata.json` сборки и сравнить проблемные с рабочими. Лишние ключи внутри `game_custom_data` (`tested_with`) лаунчер терпит
- GUI: движок ищет виджеты по имени. Устаревшая копия ванильного `.gui` без виджета = вылет, а не лог. Признак: в диффе «минус сотни строк, плюс две-три»

## Диагностика вылета

Порядок, который реально экономит раунды.

1. **`crashes/` — сначала туда, а не в логи.** В `crashes/<дата>/exception.txt` тип исключения и стек. `EXCEPTION_STACK_OVERFLOW` = рекурсия или слишком глубокая вложенность; `EXCEPTION_ACCESS_VIOLATION` = обычно что-то другое. Рядом лежит снимок `logs/` на момент падения — он полезнее текущего.
2. **Считать кадры стека:** `grep -c victoria3.exe exception.txt`. Число, упирающееся в одно и то же значение (4182 / 4187) при совершенно разных правках, означает **бесконечную рекурсию**, а не длинную цепочку: глубину задаёт лимит стека, а не скрипт. Сравнить с крэшами прошлых дней в той же папке — если картина не менялась от всех правок, причина не в них.
3. **Сводка логов вместо чтения подряд:** `sed -E 's/^\[[0-9:]+\]//' error.log | sed -E 's/[0-9]+/N/g' | sort | uniq -c | sort -rn | head -40`. Спам в 12 тысяч строк вытесняет из буфера всё остальное — сводка это показывает мгновенно.
4. **`content_load.json`** — что было включено в последнем запуске, включая пути (workshop или локальная папка).
5. **`launcher-v2.sqlite`** — полная картина плейсета. Скопировать в `/tmp` и читать:
   ```sql
   select m.displayName, m.dirPath, pm.enabled, pm.position
     from playsets_mods pm join mods m on m.id = pm.modId
    where pm.playsetId = (select id from playsets where isActive = 1)
    order by pm.position
   ```
   Здесь видно то, что иначе не видно никак: **один и тот же мод стоит дважды — из мастерской и из локальной `mod/`, и включена не та копия**; нужный компач выключен; порядок загрузки не тот, что требует README. В сессии это оказалось причиной вылета, которую я до того искал в скриптах.
6. **Циклы в чужих эффектах.** Построить граф вызовов по `scripted_effects` обоих модов и найти циклы. Если цикл есть только у чужого мода и не задевает моих ключей — это не моё, и надо сказать это прямо, а не «починить» наугад.
7. Правку своих файлов начинать, только когда пункты 1–6 сузили место. Иначе получается ремонт того, что не ломалось.

## Анализ 2: нужен ли компач вообще

`noneed` — половина папок, и это правильный результат.

- `scan_conflicts.py --a --b`. Пусто → компач не нужен, помечать `noneed`, конец
- Пересечение по путям файлов → смотреть порядок загрузки и теряется ли содержательное. Часто оба мода делают `TRY_INJECT` в один ванильный файл — конфликта нет
- Пересечение по ключам → **сравнить оба определения с ванилью построчно**, а не остановиться на факте совпадения ключа. Половина совпадений оказывается косметикой или дословным повтором ванили
- Проверить то, что скрипт не ловит: сумма товаров против 128; группы законов (`list_lawgroups_diff.py`); триггеры по `building_group`; `.gui` (`compare_gui_names.py`); id событий
- Вывод писать явно: «конфликтов нет, потому что…» с перечислением проверенного

## Анализ 3: что менять в существующем компаче

- Прочитать README компача (стимовский BBCode, он же описание в мастерской)
- По каждому файлу: на что опирается и живо ли ещё; можно ли менее инвазивно (перекрытие файла → `REPLACE:` записи → `TRY_INJECT:` → аддитивный on_action); не стало ли ненужным само по себе
- **Мердж строить на структуре того мода, который грузится последним, а из первого переносить только его содержательные отличия.** Не выносить требования первого мода наружу из чужого `OR`/гейта: так гейт обнуляется и игрок платит обе цены сразу. В комментарии писать, какая ветка чья
- Типовые находки: патч, ставший ненужным из-за наследования групп зданий (удалять целиком); список зданий, разошедшийся с новой версией (пересобрать, `INJECT:` → `TRY_INJECT:`); переопределение чужого `scripted_effect` ради одной строки (заменить своим on_action); механика на `on_yearly_pulse_country` не работает первый год — нужен парный вызов из `history/global/`; пин значения, которое и так получается само по порядку загрузки (удалять)
- Обновить `.metadata/metadata.json` (`version`, `supported_game_version`, `relationships`, `tested_with`) — и убедиться, что файл без BOM
- **Проверить копии.** Файлы компача продублированы в `__megapacks/*/` — правку синхронизировать туда же и `diff -q` следом
- Собрать чеклист проверки в игре — по убыванию риска, с явным «годно / не годно»

## Компач-замена

Когда чужой компач сам сломан и правок к нему набирается больше двух-трёх, дешевле сделать самостоятельный мод, который его заменяет, чем слой поверх.

- **Почему.** Слой требует, чтобы чужой компач был включён, стоял раньше и не менял форму. Любое из трёх нарушено — и `INJECT:` ложится на ключи, которых нет. Плюс сверху можно только добавить правильный ключ, а битый чужой остаётся и продолжает логировать
- **Как.** Свежую распаковку чужого компача класть в `_ef/<имя> out`. Генератор копирует все его файлы **байт в байт**, кроме тех, что правит; правленые пишутся **под их же именами**, чтобы ключ нигде не определялся дважды
- **Своей шапки на скопированные файлы не ставить** — именно чтобы дифф против новой версии чужого компача остался читаемым
- Битые чужие ключи теперь чинятся на месте (список замен в константе генератора), а обходные блоки из своих файлов убираются — иначе группа инжектится дважды
- В `metadata.json` и README сказать прямо: **запускать ВМЕСТО чужого компача, не вместе с ним**. Иначе каждый ключ определён дважды и побеждает случайный
- Старые файлы-слои удалить из мода (через `mv` в `_to_delete/`), иначе они переопределят то, что теперь лежит в чужих файлах

## Генераторы

Всё, что переписывает чужой мод, должно быть скриптом в `tools/`, а не ручной правкой. Правила, оплаченные раундами тестов:

- **Источник истины брать из самого чужого мода, а не из своей таблицы.** Ручной список «тег → сущность» проигрывает гонку с чужим ростером: таблица называла для Китая Da-Qing Bank (основан в 1905), а страна держит Imperial Bank of China — и так для четырёх стран. У E&F список банковских компаний лежит в `private_bank_type` в `customizable_localization`. Своя таблица допустима только для приоритета, не для членства
- Прочитанный список сверять с реально существующими ключами: у E&F в его же перечне написано `company_BankSBoBS`, а компания называется `company_BankSBoBSA`. `REPLACE:` несуществующего ключа — ошибка загрузки
- **Следить за префиксом при склейке.** `top_block()` возвращает блок ВМЕСТЕ с `REPLACE:`; ещё один прибавленный сверху даёт `REPLACE:REPLACE:building_x`, и запись молча не грузится
- Длинные `if/else_if` цепочки не строить: цепочка вкладывается, 145 веток = 145 кадров стека. Плоские `if` с флагом-переменной ведут себя так же (first-match-wins), а глубина остаётся единицей. Само по себе это не всегда причина вылета — но проверять такое дорого, а писать плоско ничего не стоит
- Генератор печатает, что именно он поправил в этот прогон, и это уходит в шапку файла. Пустой список или новый пункт = источник изменился, надо прочитать
- Самопроверка в конце прогона: баланс скобок, BOM, дубли ключей
- Удаление своего же устаревшего вывода делать через `try/except OSError` с внятным «DELETE ME» — мост не умеет unlink, и падать из-за этого весь прогон не должен

## Чего не делать

- Не «чинить» замысел автора, не разобравшись. Страна без банка может быть гейтом за игровым событием, а не багом. Сначала найти, кто и при каких условиях выдаёт нужное
- **Не удалять файл, приняв его за мусор, пока не проверено, что он не половина работающего механизма.** `zz_ef_cm_bank_group.txt` выглядел остатком эксперимента с флагом; на деле он был второй половиной владения центробанком, и его удаление вернуло «правительственное» здание. Если файл закоммичен и лежал в рабочей сборке — у него была причина
- Не восстанавливать ванильные проверки, которые **оба** мода выпилили независимо друг от друга: это компач придумывает поведение, которого не хочет ни один автор
- Не изобретать формулу, если данные есть в моде — потребности попов в `common/buy_packages/`, цены в `common/goods/`
- Не строить обратную связь от рынка — «подгонять выпуск под потребление» самораскручивается
- Не доверять чужому анализу без проверки — присланный разбор от другой модели был неверен в 4 пунктах из 7. Своей прошлой сводке и своему прошлому README тоже
- Не осторожничать с восстановлением `.gui` — разбирать дифф построчно, а не по объёму
- Не оставлять правку в одном месте — репозиторий, игровая папка и мегапаки должны совпадать всегда
- **Не чинить симптом, не поняв, симптом чего это.** Здание, которое числится правительственным при живом владельце-компании, выглядит багом; «починка» перевела прибыль центробанка компании и была откачена. Прежде чем менять поведение, отделить «panel врёт» от «panel честно показывает то, что происходит с деньгами»
- **Не гадать больше двух раз подряд.** Если две гипотезы не подтвердились, идти за фактами: crashes, sqlite плейсета, граф вызовов. Признавать «это не моё» — нормальный результат
- **Спрашивать перед архитектурной развилкой.** 95 типов компаний → 1 стоило одного вопроса и сняло три класса багов разом. Развилка «сделать проще, но иначе» — это вопрос к пользователю, а не решение в тишине

## Формат результата

Комментарии в коде и README — на английском, общение со мной — на русском. README компача — стимовский BBCode, компактно; для больших модов подробный markdown + отдельный раздел `## For Steam` с коротким BBCode-блоком. Комментарий должен отвечать «почему так, а не иначе», а не пересказывать код — особенно там, где уже наступали на грабли, с цитатой ошибки из лога (а если ошибки в логе не бывает — так и написать, что симптом молчаливый, и какой именно).

Сообщение коммита — в том же жанре: что было сломано, как это выглядело со стороны игры, почему выбрано это решение. Ревертящий коммит обязан объяснить, почему предыдущий был неправ.

Разбор конфликтов класть рядом с компачем отдельным `.md` (`conflicts_<a>_vs_<b>_report.md`): вывод `scan_conflicts.py` + раздел «почему это не конфликт / почему мерджим», таблицей «ваниль vs мод A vs мод B» по спорной записи. Статус пары дублировать строкой в таблицу «Статус пар» в сводке по каждому из двух модов.
