# Работа над компачами Victoria 3

Я поддерживаю набор компатч-модов для Victoria 3 **1.13.10**. Компач — мини-мод, стыкующий два чужих мода. Цель всегда: **минимальный компач**, чем меньше перекрывает файлов, тем меньше ломается при обновлениях.

## Папки (всё через `device_bash`, корень `$HOME/mnt`)

**Мои моды (git, сюда пишем):** `Projects/vic3_mods/`

- `_ef/`, `_morg/`, `_pbe/`, `_psc/`, `_tgr/` — компачи по парам модов; `stuff/` — прочее (bpm, mmrpa, tr, vc)
- `сводки по модам/` — по `.md` на каждый чужой мод: что меняет, версия, дата сверки
- `tools/` — скрипты анализа; `__megapacks/`, `__translations/`
- Суффиксы папок = статус: `done` / `noneed` (проверено, конфликта нет) / `out outdate`

**Чужие моды (только читать):** `Projects/vic3_mods_out/` — E&F, Morgenrote, PSC, BPM, MMRPA, PowerBlocksExpanded, TechRes+Kuromi, TheGreatRevision, TGR_Loans, _cmf, _etf, плюс `.vanillaVIC3/` (скрытая, `ls -a`) — ваниль, эталон для сравнений.

**Игра:** `mod/` — папка модов Paradox, сюда синхронизируются готовые компачи (писать всегда в оба места, потом `diff -rq`). `logs/` — error.log, game.log, debug.log. `crashes/`, `exceptions/`.

> Монтируется не всё и не всегда. Если в сессии подключён только `Projects`, `mod/` недоступен — синхронизацию в игровую папку сделать нельзя. Сказать об этом явно и попросить добавить папку, а не молча пропустить шаг.

## Технические правила

- `device_bash` = моя машина, `Bash` = облако. Разные ФС, для модов только `device_bash`
- Удалять нельзя (`rm` → Operation not permitted) → `mv` в `_to_delete/` внутри того же монтирования; `Projects/` и `mod/` — разные монтирования. **`rmdir` запрещён тоже** — после переноса файла пустая папка остаётся, игре это не мешает
- Мост периодически отваливается, подождать 60–120 сек и повторить
- `grep` с кириллицей падает («Invalid collation character») → искать через `python3`
- **У `device_bash` таймаут 45 сек.** Рекурсивный `os.walk` / `grep -r` по целому моду через монтирование в него не укладывается — сужать путь до конкретной `common/<категория>/`. Полный обход мода делать скриптами из `tools/`, они на это рассчитаны
- Перенос файла из облака на диск: `SendUserFile` → `device_commit_files` с полученным `fileUuid`. Гонять содержимое через base64 в командной строке — дорого и не нужно
- Кодировки: в игровых `.txt` (локализация, скрипты) **BOM обязателен** — `encoding='utf-8-sig'` или `printf '\xEF\xBB\xBF'`. В `.metadata/metadata.json` **BOM ЗАПРЕЩЁН**: лаунчер парсит его строгим JSON и падает на `\xEF\xBB\xBF` перед `{` — в списке модов варн «Не удалось обработать метаданные», мод не грузится. Правило: `.json` пишем только `encoding='utf-8'` (никогда `'utf-8-sig'`), после записи проверяем `b[:3] != b'\xEF\xBB\xBF'` и `json.loads`
- После каждой правки — баланс скобок: `s.count('{')-s.count('}')` должен быть 0 (комментарии срезать: `l.split('#')[0]`)

## Скрипты в `tools/`

`scan_conflicts.py --a --b` (главный: общие пути файлов и общие ключи), `check_megapack_conflicts.py` (по всей сборке), `summarize_mod_vs_vanilla.py --mod --out`, `compare_gui_names.py --a --b` (критично: пропавший виджет = вылет), `list_lawgroups_diff.py`, `scan_event_definitions.py`, `sanitize_bpm_loc.py`, `steam desc rules.txt` (BBCode).

## Факты про 1.13 (проверены, экономят часы)

- Файл перекрывается по относительному пути целиком — грубейший инструмент, только в крайнем случае
- Префиксы БД: `INJECT:` `TRY_INJECT:` `REPLACE:` `TRY_REPLACE:` `REPLACE_OR_CREATE:` — правильный способ править чужой мод. `INJECT:` в список добавляет, не заменяет
- **Ключ без префикса тоже переопределяет.** Обычное `foo = { }` в моде, загруженном позже, съедает `REPLACE_OR_CREATE:foo` из более раннего. Отсутствие префикса ≠ отсутствие конфликта
- Аддитивны: `common/on_actions/`, `GLOBAL` в `history/global/`, `BUILDINGS` в `history/buildings/`. `zz_` идёт после `99_`
- `scripted_effects/triggers/script_values`: одинаковый ключ в моде позже — переопределяет
- **Отсутствующие `has_game_rule` / script value не дают ошибки в логе.** Ветка с ними просто никогда не срабатывает. Самый тихий класс поломок — ловится только грепом имён по чужому моду
- `add_modifier { multiplier = X }` считает X **НЕ** в скоупе эффекта — внутри `every_scope_state` любое `state_*` вернёт none. Расчёт должен быть страновым
- У рынков нет переменных. Путь до владельца: `market ?= { owner ?= { } }`
- Итераторы в script value работают: `every_scope_state = { add = 1 }` (образец — ванильный `country_total_urbanization`)
- Вход в товар: `mg:X` в рынке, `sg:X` в штате
- `is_building_group` идёт по цепочке родителей — часто из-за этого патч не нужен вообще
- Потолок **128 товаров**. 130+ = вылет при входе в игру, без единой ошибки в логе. Закомментированные не считаются. Ваниль = 53
- `normal_modifier_time = 1825`, и ваниль скармливает его `days`. Если чужой мод пишет `months = normal_modifier_time` — это 152 года, то есть навсегда. В мердже такие места брать у того мода, где стоит литерал
- В `modifier_type_definitions` поля `decimals`, `color`, `percent` — **только отображение**. Расхождение по ним между модами конфликтом не является, пин-файл писать не надо
- Варн лаунчера «Не удалось обработать метаданные» = `metadata.json` не разобрался, при этом сам JSON может быть валидным. Порядок проверки: BOM (самая частая причина) → `json.loads` → набор ключей. Быстрая диагностика — прогнать разом все `metadata.json` сборки (свои + чужие моды) и сравнить проблемные с рабочими, отличие видно сразу. Лишние ключи внутри `game_custom_data` (`tested_with`) лаунчер терпит, дело не в них
- GUI: движок ищет виджеты по имени. Устаревшая копия ванильного `.gui` без виджета = вылет, а не лог. Признак: в диффе «минус сотни строк, плюс две-три»

## Анализ 1: что изменилось в чужих модах

- Взять `сводки по модам/сводка_<мод>.md` — в шапке версия и дата сверки. Файлы новее — сводку обновить
- Сверить `.metadata/metadata.json`: `version`, `supported_game_version`, `relationships`, `id`. **`id` тоже меняется** — чужой мод могли перевыложить в мастерской новой позицией, старый `id` в `relationships` компача указывает в пустоту
- Что поменялось: git по папке мода, либо прогнать `summarize_mod_vs_vanilla.py` заново
- **Первым делом — не разъехались ли имена.** Автор может переименовать весь префикс мода целиком (`kates_` → `vokaes_` у PBE), выделить часть в отдельный мод (`TGR_Loans`), убрать целую папку (`common/buildings/` у PBE). Ни одно из этих изменений не даёт ни строчки в логе: компач продолжает грузиться и молча ничего не делает. Каждое чужое имя, на которое ссылается компач, — грепом по чужому моду, поимённо
- Отдельно проверить то, на что опирается компач: списки зданий (переименовали/удалили — `TRY_INJECT` промолчит), имена PM и PMG, `building_groups` и их `parent_group`, переопределённые `scripted_triggers`, количество товаров
- Записать вывод в сводку с новой датой

## Анализ 2: нужен ли компач вообще

`noneed` — половина папок, и это правильный результат.

- `scan_conflicts.py --a --b`. Пусто → компач не нужен, помечать `noneed`, конец
- Пересечение по путям файлов → смотреть порядок загрузки и теряется ли содержательное. Часто оба мода делают `TRY_INJECT` в один ванильный файл — конфликта нет
- Пересечение по ключам → **сравнить оба определения с ванилью построчно**, а не остановиться на факте совпадения ключа. Половина совпадений оказывается косметикой или дословным повтором ванили
- Проверить то, что скрипт не ловит: сумма товаров против 128; группы законов (`list_lawgroups_diff.py`); триггеры по `building_group` (если мод A фильтрует по `bg_X`, а B добавил в дочернюю — патч не нужен); `.gui` (`compare_gui_names.py`); id событий
- Вывод писать явно: «конфликтов нет, потому что…» с перечислением проверенного — иначе через полгода то же будет проверяться заново

## Анализ 3: что менять в существующем компаче

- Прочитать README компача (стимовский BBCode, он же описание в мастерской)
- По каждому файлу: на что опирается и живо ли ещё; можно ли менее инвазивно (перекрытие файла → `REPLACE:` записи → `TRY_INJECT:` → аддитивный on_action); не стало ли ненужным само по себе
- **Мердж строить на структуре того мода, который грузится последним, а из первого переносить только его содержательные отличия.** Не выносить требования первого мода наружу из чужого `OR`/гейта: так гейт обнуляется и игрок платит обе цены сразу. В комментарии писать, какая ветка чья
- Типовые находки: патч, ставший ненужным из-за наследования групп зданий (удалять целиком); список зданий, разошедшийся с новой версией (пересобрать, `INJECT:` → `TRY_INJECT:`); переопределение чужого `scripted_effect` ради одной строки (заменить своим on_action — аддитивен и чинит случаи, где чужой эффект вызывался не всегда); механика на `on_yearly_pulse_country` не работает первый год — нужен парный вызов из `history/global/`; пин значения, которое и так получается само по порядку загрузки (удалять)
- Обновить `.metadata/metadata.json` (`version`, `supported_game_version`, `relationships`, `tested_with`) — и убедиться, что файл без BOM
- **Проверить копии.** Файлы компача продублированы в `__megapacks/*/` — правку синхронизировать туда же и `diff -q` следом. Мегапаки при этом живут своим циклом обновления, их `metadata.json` может отставать на версию игры: это отдельная работа, о ней сказать отдельно, а не тянуть в текущую
- Собрать чеклист проверки в игре — по убыванию риска, с явным «годно / не годно»

## Чего не делать

- Не «чинить» замысел автора, не разобравшись. Страна без банка может быть гейтом за игровым событием, а не багом. Сначала найти, кто и при каких условиях выдаёт нужное
- Не восстанавливать ванильные проверки, которые **оба** мода выпилили независимо друг от друга: это компач придумывает поведение, которого не хочет ни один автор. Отметить в комментарии и пройти мимо
- Не изобретать формулу, если данные есть в моде — потребности попов в `common/buy_packages/`, цены в `common/goods/`
- Не строить обратную связь от рынка — «подгонять выпуск под потребление» самораскручивается: в залитом рынке потребление меряет доступность, а не потребность
- Не доверять чужому анализу без проверки — присланный разбор от другой модели был неверен в 4 пунктах из 7. Своей прошлой сводке и своему прошлому README тоже: они описывают мод той версии, что была тогда
- Не осторожничать с восстановлением `.gui` — разбирать дифф построчно, а не по объёму
- Не оставлять правку в одном месте — репозиторий, игровая папка и мегапаки должны совпадать всегда

## Формат результата

Комментарии в коде и README — на английском, общение со мной — на русском. README компача — стимовский BBCode, компактно; для больших модов подробный markdown + отдельный раздел `## For Steam` с коротким BBCode-блоком. Комментарий должен отвечать «почему так, а не иначе», а не пересказывать код — особенно там, где уже наступали на грабли, с цитатой ошибки из лога (а если ошибки в логе не бывает — так и написать, что симптом молчаливый, и какой именно).

Разбор конфликтов класть рядом с компачем отдельным `.md` (`conflicts_<a>_vs_<b>_report.md`): вывод `scan_conflicts.py` + раздел «почему это не конфликт / почему мерджим», таблицей «ваниль vs мод A vs мод B» по спорной записи. Статус пары дублировать строкой в таблицу «Статус пар» в сводке по каждому из двух модов.
