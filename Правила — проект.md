# Правила — проект

Как ведётся документация и чем меряется набор. Правила про сами моды и движок
Victoria 3 — навык `vic3-modding` плагина vic3tools, сборка и компачи — навык
`vic3-compat`; читаются, когда разбираешь конфликт или собираешь.

### `blocks.json` — единственный источник правды о наборе

Три ключа, которые легко перепутать:

* `order` — только порядок колонок в матрице;
* `load_order` — **истинный порядок загрузки**, на нём работают `v3 winner` и `v3 audit holes`. Содержит ваниль,
  фреймворки, все моды, **мегапак, три собранных аддона и оба чужих компача LLWA**;
* `labels` — короткие ярлыки для отчётов.

Псевдоблоки `_сборки_не_блоки` и `_чужие_компачи_не_блоки` в матрицу не идут, но `v3 audit holes` меряет их наравне со
всеми — именно из-за них нашлись GR.16 и HC.12. Экспериментировать с составом — на копии файла в `_tmp_analysis/`.

### `v3 audit holes` — разделы

* **economy** (`--require-pmg pmg_market_liquidity --require-pmg 'pmg_private_ownership_*'`) — приватно владеемое здание (`ownership_type = self`) без `pmg_market_liquidity` или без
  `pmg_private_ownership_*` в **итоговом** теле. Это класс LLWA.6 / GR.15 / HC.12. Штатные исключения: ванильные
  subsistence-постройки, `building_art_academy`, `building_sulfur_mine` и все `building_financial_centre_*` у E&F —
  они вне финансовой системы по замыслу.
* **builds** — пары «мегапак/аддон × всё, что грузится позже». Считает только замещающие префиксы: `INJECT:`
  складывается и потерей не является.
* **pmg / companies** — что теряется под последним замещающим телом.
* **new** — ключи, которых нет ни у кого другого в цепочке. Шумный раздел: собственный контент мода, который никто не
  упоминает, — норма.

## 3. README компача

Порядок жёсткий: заголовок → шапка → описание для мастерской → подробности.

```markdown
# <Название, как в мастерской>

<!-- meta
пара: LLWA × E&F          ← или «сборка: аддон LLWA», или «мод: свой хотфикс E&F 1.13»
статус: done              ← done | noneed | out | out fixed | out outdate | собран
версии: Game 1.13 (exe 1.13.11) — LLWA 2.6.3, E&F V4
позиция: грузится после …
файлов: 4
генератор: tools/regen_llwa_ef.py
зависит от: —
-->

## Для мастерской

[h1]…[/h1]  BBCode, копируется в мастерскую как есть

---

## Load order
## Что теряется без этого компача
## Что внутри
## Как сделан мердж
## Что намеренно не тронуто
## Открытые вопросы
## Пересборка
```

Шапка `<!-- meta … -->` — не украшение: по ней работает `docs_index.py`, то есть
вопрос «что у нас есть и в каком состоянии» стоит один прогон вместо сорока восьми
чтений. **Поля не переименовывать и не удалять**; неизвестное значение — прочерк,
а не отсутствующая строка. Первое поле — одно из трёх: `пара` (компач),
`сборка` (аддон или мегапак), `мод` (наш собственный мод, не компач).

Описание для мастерской идёт **первым** блоком после шапки: в мастерскую копируется
оно, и искать его в конце файла каждый раз — лишняя работа. У компача со статусом
`noneed` его нет и не должно быть — такой компач не публикуется, его README целиком
это обоснование статуса.

Часть старых README — целиком BBCode, без подробностей. У них раздел `## Подробности`
помечен явно: «подробного разбора не писали». Это честнее пустого шаблона и видно
грепом; заполнять по мере того, как компач попадает в работу.

## 4. Разбор конфликтов — временный файл

Живёт рядом с компачем, пока пара в работе. Содержит **только** конфликты и дырки
контента: пересечения ключей, пересечения путей, новый контент, которого нет в
чужих списках. **Как это закрыто — не здесь, а в README.**

Пара закрыта → файл удаляется (итог — в README компача, сам разбор — в истории git).
Рядом с готовым компачем он не лежит.

Имя, пока файл живой: `conflicts_<A>_vs_<B>.md`.

## 5. План и архив

**История — только в архиве.** План, README, правила и навыки держат текущее: открытые задачи, как устроено
сейчас, как работать. Ход работы, прогоны по датам, итоги ночей, «состояния на дату», закрытые задачи — в архив
(уборка 5.10.2026: история копилась в плане и README и забивала контекст).

**План — разделы: целевой порядок запуска, матрица, этапы пачки П0–П5 (открытые задачи по этапам).** Этапы форка, его решения,
понятия и история — в репо форка (его `CLAUDE.md`: понятия — одна заметка на понятие, решения — реестр с действующим
видом и «заменено», история — `история/`). README — одно текущее «Состояние», без дат прошлых сессий.
Закрытый открытый вопрос либо становится задачей, либо уходит в
`docs/история/справка — решения и набор.md` с итогом.

**В плане живут только активные задачи.** Группа задач закрыта (этап, ночь, аддон собран,
блок закрыт) → уезжает в `docs/история/ГГГГ-ММ-ДД <тема>.md` (дата закрытия) целиком, вместе с опытом,
отменёнными гипотезами и «не делать в этом аддоне». В плане — ничего (если от группы остались
открытые хвосты — они задачами в своих блоках).

`docs/история/README.md` — **хронология**: строка на дату (что было, ссылка на файл, отчёт ночи) и раздел «Справка» —
действующие решения и разборы механики.

**Опыт по сессии сортируется по природе, а не по дате:**

* воспроизводимое правило → в правила (проект или моды, по смыслу);
* решение о порядке и составе набора («почему VC до HC») → `docs/история/справка — решения и набор.md`;
* решение по этому набору, которое действует, — в задачу плана, пока она открыта; потом — в архив со справкой;
* история конкретной работы → в архив вместе с задачами группы.

Архив контекст не ест, пока на него нет ссылки. Поэтому в архив можно переносить
щедро, а вот ссылаться на него из плана — только когда это правда нужно.

**Нумерация задач** — по блоку: `EF.n`, `GR.n`, `HC.n`, `LLWA.n`, `VC.n`, `TGR.n`, `USU.n`,
`МП.n` (мегапак), `ТЕХ.n` (технологии), `TR.n` (T&R), `ИИ.n` (ИИ пачки), `ИНСТ.n` (инструменты и генераторы
этого репо), `ВЫК.n` (выкладки: мастерская, Google Диск), `ОТЗ.n` (отзывы игроков, `Отзывы игроков.md`).
Номера не переиспользуются: закрытая задача уезжает в архив вместе с номером,
новая получает следующий свободный.

**Статусы пар** — таблица в разделе 7 ниже.

`noneed` ставится только после прогона обоих инструментов. Матрица закрывает класс
«оба трогают одну запись», `v3 audit holes` — «один добавил контент, которого
нет в чужих списках». Один без другого `noneed` не обосновывает: так дважды
пришлось снимать уже поставленный статус (LLWA × E&F, HC+GoB+MoH × E&F).

## 6. Чего не писать

* Пересказ того, что видно в файлах мода — вместо этого имя файла и строка.
* «Как закрыто» в разборе конфликтов и «какие были конфликты» в README — каждое в своём файле.
* Датированные копии отчётов рядом с актуальным (`*_pre_*`, `*_2026-08-21`) — сразу удалять (история в git).
* Числа, которые считает инструмент. Если число нужно — назвать команду, которая его печатает.

## 7. Статусы пары

| статус | значение |
| --- | --- |
| `noneed` | проверено, компач не нужен. **Обязательно записать, почему** — с перечислением проверенного |
| `done` | компач написан и лежит в `_<блок>/` |
| `есть` | компач написан автором чужого мода, свой не нужен |
| `out` / `out outdate` | чужой компач распакован как источник; `outdate` = требует пересборки |
| `нужен` | разобран, не написан |

`noneed` — примерно половина пар, и это правильный результат.

**`noneed` часто держится на порядке загрузки, а не на отсутствии пересечения.** «PSC грузится после TGR и выигрывает, терять нечего» — законный вывод, но его надо записать явно и назвать, какой порядок имеется в виду. Иначе в сборке тот же ключ всплывёт снова, и придётся выяснять заново. Такие требования к порядку выносятся в README сборки отдельной строкой.

## 8. Технические правила окружения

**Три режима запуска, равноправные** (пользователь 5.10): работа идёт и так, и так — правила ниже должны держаться
в каждом.

| режим | где агент | ПК, игра, сейвы, `vic3_mods_out` | Python |
| --- | --- | --- | --- |
| **локально** (Claude Code на ПК) | основная копия `C:/ProjectData/vic3/vic3_mods` (общая со мной и рабочими, с 21.10) | напрямую: PowerShell, `vic3_tools/bridge/game/run_vic3_sandbox.ps1` + хуки форка | `py` |
| **Remote Control** (локальная сессия на ПК, управляется с телефона/веба) | то же, что локально | напрямую — как локально | `py` |
| **облако** (claude.ai/code) | Linux-клон репозитория | только через мост `vic3-pc` (`vic3_tools/bridge/pc` + `bridge.toml`, навык `vic3-sandbox`, «Из облачной сессии»): прогоны, логи, сейвы, `orig/…`, `workshop/…`, генераторы на ПК (`py_tool` + `wt_diff`), живая копия — `sync_mod`. Плагин vic3tools (навыки, хуки) и `v3` — скрипт настройки среды claude.ai/code (`vic3_tools/claude-plugin/cloud-setup.sh`, его README «Cloud sessions»): `.claude/settings.json` репо плагины в облаке не включает | `python3` |

**Общее для всех:** одна ветка `main` на GitHub; в начале сессии `git pull`, после каждого коммита — `git push` в `main` — иначе другие режимы и мост не видят
работу. Мост работает из основной копии на ПК, а ветки разворачивает в свою `_bridge/wt` — локальная сессия и мост
друг другу не мешают, кроме одного: живую копию мода и игру не трогать двумя режимами сразу.

**Облако: ветка сессии `claude/*` не используется** (решение пользователя 7.10: ветки множились от каждой сессии, агенты
путались, ночная сессия не видела работу дневной) — правило в `CLAUDE.md`. Висящую ветку вливать fast-forward или merge,
без rebase; удалять ветки из облака прокси не даёт (403) — удаляет пользователь на GitHub.

**Локально и Remote Control** (Windows): Git Bash и PowerShell, репозиторий
`C:/ProjectData/vic3/vic3_mods`, живые копии модов — `Documents/Paradox Interactive/Victoria 3/mod/`,
мастерская — `C:/Games/Steam/steamapps/workshop/content/529340/`, ваниль —
`C:/Games/Steam/steamapps/common/Victoria 3/game/`, логи — `Documents/…/Victoria 3/logs/`.

* **Python — `py`**, не `python3` (его нет, вместо него всплывает заглушка Microsoft Store).
  `node` тоже есть. `bc` нет.
* **Скрипт с обратными слешами или сложными кавычками — файлом через Write**, а не heredoc в
  Git Bash: в heredoc `'\\'` и похожие последовательности ломаются даже в `<<'PY'`.
  Черновики и одноразовые скрипты — в scratchpad сессии или `Projects/vic3/_tmp_analysis/`.
* **CRLF.** `sed` Git Bash молча переводит CRLF в LF; побайтовую копию чужого файла правкой
  строк делать `sed -b` или Python в бинарном режиме. `grep -c $'\r'` в Git Bash врёт (показывает 0
  на CRLF-файле) — проверять `py` (`b.count(b'\r\n')`).
* **Какая копия мода реально загрузилась — смотреть `Documents/…/Victoria 3/content_load.json`**
  (`enabledMods[].path`, пишется лаунчером при каждом запуске). Локальная копия и копия из

## 9. Формат результата

* Комментарии в коде и README — на английском, общение со мной — на русском
* README компача — стимовский BBCode, компактно; для больших модов подробный markdown + отдельный раздел `## For Steam` с коротким BBCode-блоком
* Комментарий должен отвечать «почему так, а не иначе», а не пересказывать код — особенно там, где уже наступали на грабли, с цитатой ошибки из лога (а если ошибки в логе не бывает — так и написать, что симптом молчаливый, и какой именно)
* Сообщение коммита — в том же жанре: что было сломано, как это выглядело со стороны игры, почему выбрано это решение. Ревертящий коммит обязан объяснить, почему предыдущий был неправ
* Письмо автору чужого мода — на английском, по-коллегиальному, без поучений: что я сделал и как это устроено → цифры → **список найденных багов в его моде** (для него это самое ценное) → ссылка на репозиторий с «берите что нужно». Каждый баг одной фразой: где, что не так, как проявляется. Свои решения подавать как «вот что вышло», а не как «вам надо сделать так»
* Разбор конфликтов класть рядом с компачем отдельным `.md` (`conflicts_<A>_vs_<B>.md`, временный файл — см. раздел 4): вывод анализа + раздел «почему это не конфликт / почему мерджим», таблицей «ваниль vs мод A vs мод B» по спорной записи. Статус пары дублировать в `../docs/этапы/Этап П. Пачка.md` (узел)
* Для сборки — `conflicts_<имя>_internal.md` в её корне: машинный вывод `v3 audit dups` (было `check_megapack_conflicts.py`), а под ним разбор из четырёх частей: **«требуют работы — сделано»**, **«не конфликты»** таблицей, **«пересечения сборки с самими модами»**, **«проверки сборки»** — числа: файлов, баланс скобок, кодировки, дубли локализации по языкам, товары против 128, покрытие компачей с перечислением всех законных отклонений
* Открытые вопросы, которые не удалось закрыть, писать отдельным разделом с явной пометкой, на что они влияют, а на что нет
