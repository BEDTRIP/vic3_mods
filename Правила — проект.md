# Правила — проект

Как ведётся документация и чем меряется набор. Правила про сами моды и движок
Victoria 3 — в `Правила работы с модами Victoria 3.md`, это отдельный файл и
читается только когда разбираешь конфликт.

---

## 1. Что где лежит и что читать когда

| файл | что там | когда читать |
| --- | --- | --- |
| `README.md` | точка входа: карта, состояние, чеклист начала сессии | **всегда, первым** |
| `Правила — проект.md` | этот файл: инструменты, шаблоны, архив | когда пишешь документацию или зовёшь инструмент |
| `Правила работы с модами Victoria 3.md` | движок, порядок загрузки, префиксы, факты 1.13, диагностика | когда разбираешь конфликт |
| `План проекта.md` | матрица пар, статусы, **активные** задачи, решения | когда берёшь задачу |
| `архив/` | завершённые группы задач и опыт по ним | **только по явной ссылке из плана** |
| `сводки по модам/` | что делает каждый чужой мод | когда мод впервые попадает в работу |

Правило экономии: обязателен к чтению один файл — корневой `README.md`.
Всё остальное подтягивается по ссылке под конкретную задачу. Если для ответа
пришлось прочитать три больших файла — значит, чего-то не хватает в `README.md`,
и это надо дописать туда, а не запоминать.

### `blocks.json` — единственный источник правды о наборе

Три ключа, которые легко перепутать:

* `order` — только порядок колонок в матрице;
* `load_order` — **истинный порядок загрузки**, на нём работают `vfs_order.py` и
  `content_holes.py`. Содержит ваниль, фреймворки, все моды, **мегапак, три
  собранных аддона и оба чужих компача LLWA**;
* `labels` — короткие ярлыки для отчётов.

Псевдоблоки `_сборки_не_блоки` и `_чужие_компачи_не_блоки` в матрицу не идут, но
`content_holes.py` меряет их наравне со всеми — именно из-за них нашлись GR.16 и HC.12.

**Кэш индексов:** имя = `basename` + `md5(абсолютный путь)[:12]`. Переписал пути —
весь кэш инвалидируется, каждый мод индексируется заново (Morgenröte один под 40 с).
Экспериментировать с составом на копии файла в `_tmp_analysis/`, пути в ней держать теми же.

### `content_holes.py` — разделы

```
python3 tools/content_holes.py --only registry        # главный: приватные здания вне экономики E&F
python3 tools/content_holes.py --only builds          # сборки против того, что грузится после них
python3 tools/content_holes.py --only pmg --strict    # съеденные production_method_groups
python3 tools/content_holes.py --only companies --strict
python3 tools/content_holes.py --only new --source USU
```

* **registry** — приватно владеемое здание (`ownership_type = self`) без
  `pmg_market_liquidity` или без `pmg_private_ownership_*` в **итоговом** теле.
  Это класс LLWA.6 / GR.15 / HC.12. Штатные исключения, которые он всегда показывает:
  ванильные subsistence-постройки, `building_art_academy`, `building_sulfur_mine`
  и все `building_financial_centre_*` у E&F — они вне финансовой системы по замыслу.
* **builds** — пары «мегапак/аддон × всё, что грузится позже». Считает только
  замещающие префиксы: `INJECT:` складывается и потерей не является.
* **pmg / companies** — что теряется под последним замещающим телом. `--strict`
  оставляет только случаи, где пострадал вклад сборки или компача, то есть уже
  сделанная работа; без него в выдачу попадает любой чужой редизайн ванильной записи.
* **new** — ключи, которых нет ни у кого другого в цепочке, с колонкой «кто упоминает».
  Шумный раздел: собственный контент мода, который никто не упоминает, — норма.

**Кэш версионируется:** константа `CACHE_VERSION` в начале файла. Поменял парсер —
подними версию, старые файлы кэша просто перестанут находиться. Удалить их с
монтирования нельзя (`Operation not permitted`) — переносить в `tools/_to_delete/`.

Полный прогон не влезает в один вызов device_bash: первый вызов индексирует часть
модов и падает по таймауту, второй доиндексирует остальные и печатает отчёт. Это
нормально, кэш пишется атомарно после каждого мода.

## 3. README компача

Порядок жёсткий: заголовок → шапка → описание для мастерской → подробности.

```markdown
# <Название, как в мастерской>

<!-- meta
пара: LLWA × E&F          ← или «сборка: аддон LLWA», или «мод: свой хотфикс E&F 1.13»
статус: done              ← done | noneed | out | out fixed | out outdate | собран
версии: Game 1.13 (exe 1.13.11) — LLWA 2.6.3, E&F V4
позиция: грузится после …
файлов: 4
генератор: tools/regen_llwa_ef.py
зависит от: —
-->

## Для мастерской

[h1]…[/h1]  BBCode, копируется в мастерскую как есть

---

## Load order
## Что теряется без этого компача
## Что внутри
## Как сделан мердж
## Что намеренно не тронуто
## Открытые вопросы
## Пересборка
```

Шапка `<!-- meta … -->` — не украшение: по ней работает `docs_index.py`, то есть
вопрос «что у нас есть и в каком состоянии» стоит один прогон вместо сорока восьми
чтений. **Поля не переименовывать и не удалять**; неизвестное значение — прочерк,
а не отсутствующая строка. Первое поле — одно из трёх: `пара` (компач),
`сборка` (аддон или мегапак), `мод` (наш собственный мод, не компач).

Описание для мастерской идёт **первым** блоком после шапки: в мастерскую копируется
оно, и искать его в конце файла каждый раз — лишняя работа. У компача со статусом
`noneed` его нет и не должно быть — такой компач не публикуется, его README целиком
это обоснование статуса.

Часть старых README — целиком BBCode, без подробностей. У них раздел `## Подробности`
помечен явно: «подробного разбора не писали». Это честнее пустого шаблона и видно
грепом; заполнять по мере того, как компач попадает в работу.

## 4. Разбор конфликтов — временный файл

Живёт рядом с компачем, пока пара в работе. Содержит **только** конфликты и дырки
контента: пересечения ключей, пересечения путей, новый контент, которого нет в
чужих списках. **Как это закрыто — не здесь, а в README.**

Пара закрыта → файл переносится в `tools/_to_delete/разборы конфликтов/<путь>/`.
Ничего не пропадает, но и рядом с готовым компачем не лежит. Удалять с
монтирования нельзя — только переносить.

Имя, пока файл живой: `conflicts_<A>_vs_<B>.md`.

## 5. План и архив

**В плане живут только активные задачи.** Группа задач закрыта (аддон собран,
блок закрыт) → уезжает в `архив/<имя группы>.md` целиком, вместе с опытом,
отменёнными гипотезами и «не делать в этом аддоне». В плане остаётся одна строка
со ссылкой.

`архив/README.md` — индекс: одна строка на файл, что там и когда закрыто.

**Опыт по сессии сортируется по природе, а не по дате:**

* воспроизводимое правило → в правила (проект или моды, по смыслу);
* решение по этому набору («почему VC до HC») → в план, в таблицу решений;
* история конкретной работы → в архив вместе с задачами группы.

Архив контекст не ест, пока на него нет ссылки. Поэтому в архив можно переносить
щедро, а вот ссылаться на него из плана — только когда это правда нужно.

**Нумерация задач** — по блоку: `GR.n`, `HC.n`, `LLWA.n`, `VC.n`, `МП.n`.
Номера не переиспользуются: закрытая задача уезжает в архив вместе с номером,
новая получает следующий свободный.

**Статусы пар** — таблица в разделе 7 ниже.

`noneed` ставится только после прогона обоих инструментов. Матрица закрывает класс
«оба трогают одну запись», `content_holes.py` — «один добавил контент, которого
нет в чужих списках». Один без другого `noneed` не обосновывает: так дважды
пришлось снимать уже поставленный статус (LLWA × E&F, HC+GoB+MoH × E&F).

## 6. Чего не писать

* Пересказ того, что видно в файлах мода — вместо этого имя файла и строка.
* «Как закрыто» в разборе конфликтов и «какие были конфликты» в README — каждое в своём файле.
* Датированные копии отчётов рядом с актуальным (`*_pre_*`, `*_2026-08-21`) — сразу в `_to_delete`.
* Числа, которые считает инструмент. Если число нужно — назвать команду, которая его печатает.

## 7. Статусы пары

| статус | значение |
| --- | --- |
| `noneed` | проверено, компач не нужен. **Обязательно записать, почему** — с перечислением проверенного |
| `done` | компач написан и лежит в `_<блок>/` |
| `есть` | компач написан автором чужого мода, свой не нужен |
| `out` / `out outdate` | чужой компач распакован как источник; `outdate` = требует пересборки |
| `нужен` | разобран, не написан |

`noneed` — примерно половина пар, и это правильный результат.

**`noneed` часто держится на порядке загрузки, а не на отсутствии пересечения.** «PSC грузится после TGR и выигрывает, терять нечего» — законный вывод, но его надо записать явно и назвать, какой порядок имеется в виду. Иначе в сборке тот же ключ всплывёт снова, и придётся выяснять заново. Такие требования к порядку выносятся в README сборки отдельной строкой.

## 8. Технические правила окружения

* `device_bash` = моя машина, `Bash` = облако. Разные ФС, для модов только `device_bash`
* **`device_bash` убивает все процессы вызова, когда вызов заканчивается.** `nohup ... &`, `setsid`, `disown` не помогают — фоновый процесс не переживает возврат тулзы, файл вывода остаётся нулевой длины. Длинную работу резать на куски, каждый под 45 секунд, и складывать результат в кэш на диске. Ловушка при проверке: `pgrep -f <имя>` матчит саму команду `bash -c`, в которой это имя написано, и всегда отвечает «работает» — проверять через `ps -eo pid,etime,cmd | grep ... | grep -v grep`
* **У `device_bash` таймаут 45 сек.** Рекурсивный обход целого мода через монтирование в него не укладывается — сужать путь до конкретной `common/<категория>/` или пользоваться кэширующими скриптами из `tools/`. Индекс большого мода (Morgenröte, 8200 файлов) — 30–40 сек, поэтому кэш индексов обязателен
* **`/tmp` на монтировании не пишется** — временные файлы класть в `Projects/_tmp_analysis/`
* Удалять нельзя (`rm` → Operation not permitted) → `mv` в `_to_delete/` внутри того же монтирования; `Projects/` и `mod/` — разные монтирования. **`rmdir` запрещён тоже** — после переноса файла пустая папка остаётся. Игре это не мешает, но `diff -rq` на ней ругается («Only in ...») — это не расхождение
* Мост периодически отваливается, подождать 60–120 сек и повторить
* `grep` с кириллицей падает («Invalid collation character») → искать через `python3`
* Перенос файла из облака на диск: `SendUserFile` → `device_commit_files` с полученным `fileUuid`. Гонять содержимое через base64 — дорого и не нужно
* **Кодировки.** В игровых `.txt` / `.yml` BOM нужен там, где в файле есть не-ASCII — `encoding='utf-8-sig'` или `printf '\xEF\xBB\xBF'`. Чистый ASCII работает и без BOM, и **побайтовым копиям чужих файлов BOM добавлять нельзя**. Самопроверка ищет не «файл без BOM», а «файл без BOM, в котором есть байт >127 в НЕкомментарной строке». ASCII-арт в шапках чужих файлов под это не попадает. В `.metadata/metadata.json` **BOM ЗАПРЕЩЁН**: лаунчер парсит его строгим JSON и падает на `\xEF\xBB\xBF` перед `{`. Правило: `.json` писать только `encoding='utf-8'`, после записи проверять `b[:3] != b'\xEF\xBB\xBF'` и `json.loads`
* После каждой правки — баланс скобок: `s.count('{')-s.count('}')` должен быть 0 (комментарии срезать: `l.split('#')[0]`). Плюс **проверка на дубли top-level ключей по всему моду**

### Python на этих файлах

* **`io.open(path,'w',...)` труncate'ит файл ДО проверки аргументов.** Опечатка в `newline='\\n'` → `ValueError`, а файл уже нулевой длины. Так был обнулён генератор на 2282 строки. Правило: писать во временный файл рядом и `os.replace(tmp, path)`
* Heredoc для python-скриптов только в кавычках (`<<'PY'`), иначе bash съест `$` и backticks
* Многошаговые правки одного файла делать одним скриптом с `assert old in s` на каждый кусок
* Текст с игровым синтаксисом (`\xEF`, `\[`, `\d`) внутри python-скрипта держать в raw-строке

### git на монтировании

* `.git/index.lock` и `.git/HEAD.lock` остаются после сбоя и не удаляются → `mv` в `.git/_stale/` перед каждой git-командой
* `git checkout -- <file>` падает («unable to unlink old») → восстанавливать через `git show HEAD:<path> > <path>`
* Коммит без `user.name`/`user.email` → `git -c user.name=... -c user.email=... commit`, значения брать из `git log -1 --format='%an <%ae>'`
* Backticks в `git commit -m` исполняются bash → сообщение всегда через `-F /tmp/msg.txt` с quoted heredoc
* `warning: unable to unlink .git/objects/**/tmp_obj_*` — безвредно
* `.gitattributes` конвертирует CRLF→LF при индексации: `git diff --stat` покажет правку в один символ на файле, который я не трогал. Это перенос строк, а не правка

## 9. Формат результата

* Комментарии в коде и README — на английском, общение со мной — на русском
* README компача — стимовский BBCode, компактно; для больших модов подробный markdown + отдельный раздел `## For Steam` с коротким BBCode-блоком
* Комментарий должен отвечать «почему так, а не иначе», а не пересказывать код — особенно там, где уже наступали на грабли, с цитатой ошибки из лога (а если ошибки в логе не бывает — так и написать, что симптом молчаливый, и какой именно)
* Сообщение коммита — в том же жанре: что было сломано, как это выглядело со стороны игры, почему выбрано это решение. Ревертящий коммит обязан объяснить, почему предыдущий был неправ
* Письмо автору чужого мода — на английском, по-коллегиальному, без поучений: что я сделал и как это устроено → цифры → **список найденных багов в его моде** (для него это самое ценное) → ссылка на репозиторий с «берите что нужно». Каждый баг одной фразой: где, что не так, как проявляется. Свои решения подавать как «вот что вышло», а не как «вам надо сделать так»
* Разбор конфликтов класть рядом с компачем отдельным `.md` (`conflicts_<A>_vs_<B>.md`, временный файл — см. раздел 4): вывод анализа + раздел «почему это не конфликт / почему мерджим», таблицей «ваниль vs мод A vs мод B» по спорной записи. Статус пары дублировать в `План проекта.md`
* Для сборки — `conflicts_<имя>_internal.md` в её корне: машинный вывод `check_megapack_conflicts.py`, а под ним разбор из четырёх частей: **«требуют работы — сделано»**, **«не конфликты»** таблицей, **«пересечения сборки с самими модами»**, **«проверки сборки»** — числа: файлов, баланс скобок, кодировки, дубли локализации по языкам, товары против 128, покрытие компачей с перечислением всех законных отклонений
* Открытые вопросы, которые не удалось закрыть, писать отдельным разделом с явной пометкой, на что они влияют, а на что нет
* **В конце сессии — обновить этот файл и `План проекта.md`.** Всё, что узнали, должно оказаться здесь; иначе следующая сессия начнёт с нуля
