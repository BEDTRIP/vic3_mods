# План инструментов для модов Victoria 3

Черновик для будущего отдельного репо инструментов (рабочее имя `vic3-tools`). Когда репо появится — переехать туда
первым документом, здесь оставить ссылку.

## Зачем

Агент (облачный и локальный) и человек тратят время и токены на одно и то же: найти определение, прочитать огромный
файл ради одного блока, узнать об ошибке только из `error.log` после прогона, сверстать GUI вслепую. Инструменты
должны:

1. **Отвечать коротко** — `путь:строка` и выжимка, а не файл целиком. Вывод по умолчанию рассчитан на агента
   (ограничен по объёму), `--json` — для других инструментов.
2. **Ловить ошибки до прогона** — проверки скрипта, локализации и GUI, автоматически после правки (хук).
3. **Показывать GUI без прогона** — сначала стенд на живой игре через мост, потом свой рендер `.gui` → PNG.
4. **Быть общими** — работать с любым модом и плейсетом; проектное (компачи, модель денег форка) — снаружи, поверх
   общего ядра.

Мерило: токены и ходы на три эталонные задачи (найти, где определено и кем используется; поправить виджет в
панели; найти причину ошибки из `error.log`) — замер до и после этапов 2–4.

Что мешает сейчас:

- **Нет общего ядра.** Два парсера (`ld_pdx.py`, `vic3lib.py`) и регулярки в отдельных скриптах; каждый скрипт сейва
  заново читает сейв на сотни мегабайт.
- **Пути зашиты в код** (`FORK = ../..`, `GAME = C:\games\…`), разные в каждом скрипте.
- **Разовое вперемешку с постоянным:** пробы этапов (`ld_probe_*`, `ld_r1a_checks.py`) рядом с ядром; `_to_delete/`.
- **История в docstring'ах** — номера этапов и даты вместо описания.
- **Нет тестов.**
- **Нет ничего для GUI**, кроме `compare_gui_names.py` и `ld_vitrine.py`. **Нет справочника ванили** — агент ищет в
  файлах игры через мост или по памяти.
- **Мост рассчитан на прогоны:** короткий цикл «правка → картинка» им не сделать; список скриптов, которые можно
  запускать на ПК, — шесть имён.

## Устройство нового репо

```
vic3tools/              пакет Python
  core/                 лексер и парсер с позициями; порядок загрузки (VFS); конфиг путей
  index/                индекс SQLite: определения, ссылки, локализация, GUI-типы и шаблоны, текстуры, defines
  lint/                 правила проверок и один запускатель
  gui/                  оглавление, раскрытие шаблонов, справочник ванили, правка по пути, позже рендер
  compat/               конфликты, матрица пар, кто выигрывает ключ, merge
  save/                 разбор текстового сейва, кеш, запросы
  logs/                 error.log по семействам, сравнение прогонов, места ошибок в коде
  gen/                  каркас генераторов: emit, --check
bridge/                 MCP-сервер ПК (обобщённый мост) и скрипты игры (PowerShell)
claude-plugin/          плагин Claude Code: навыки, хуки, MCP (мост), LSP (CWTools, если подойдёт)
tests/                  тесты на маленьких примерах
```

- **Одна команда** `v3 <подкоманда>` (`v3 def`, `v3 refs`, `v3 outline`, `v3 lint`, `v3 winner`…), у каждой
  `--help`, короткий вывод и `--json`.
- **Конфиг** `vic3tools.toml` у проекта: путь к игре, к документам игры, к модам, плейсет. Ни одного пути в коде.
- **Проекты подключают пакет** (`pip install -e ../vic3-tools`) и держат своё: генераторы компачей — в `vic3_mods`,
  разборы `eflog` и проверки документов — у форка.
- **Файлы игры в репо не кладутся** (это чужой контент): индекс и справочник строятся из игры на месте — на ПК, в
  облаке из копии ванили, если её туда положить (вопрос ниже).

## Этапы

Порядок — по выигрышу на вложенный труд. «Где» — что нужно для работы: облако справится само или нужен ПК.

| # | этап | что получается | где |
| --- | --- | --- | --- |
| 0 | **Каркас** | репо, пакет, `v3`, конфиг путей, линтер кода и pytest в CI, пустой плагин | облако |
| 1 | **Ядро и совместимость** | один парсер (из `ld_pdx.py` + `vic3lib.py`), VFS по плейсету; на нём — `scan_conflicts`, `pair_matrix`, `vfs_order`, `replace_audit`, `stale_bodies`, `loc_dead_overrides`; старые копии в `vic3_mods` вызывают пакет | облако |
| 2 | **Индекс** | SQLite по ванили и плейсету; `v3 def X`, `v3 refs X`, `v3 loc KEY`, `v3 outline <файл>` (дерево записей и виджетов с диапазонами строк); правило в CLAUDE.md проектов «большой файл — сначала `outline`» | ПК один раз (ваниль), дальше облако — **главная экономия токенов** |
| 3 | **GUI** | `v3 gui resolve` (виджет с подставленными `using` / `blockoverride`), справочник ванильных типов, шаблонов и текстур с образцами, `v3 gui set <файл> <путь> prop=…`, проверка: влезает ли текст на 11 языках в ширину | облако + выгрузка ванили |
| 4 | **Проверки и хук** | `v3 lint`: скобки, неизвестные эффекты / триггеры / ключи, отсутствующая локализация, дубли GUI-типов, `[GetX.Y]` по выгрузке типов данных игры; хук после правки в плагине | выгрузки с ПК (консольные `script_docs`, `DumpDataTypes` — проверить на 1.13) |
| 5 | **Проба CWTools** | на ПК: запустить сервер CWTools вне VS Code на форке с ванилью, посчитать ложные срабатывания; если терпимо — LSP в плагине (ошибки агенту после каждой правки, переход к определению) | ПК, можно параллельно с 2–4 |
| 6 | **Мост v2** | любые команды `v3` вместо шести имён; режим «стенд»: игра в отладочном режиме на сейве, файл GUI перечитывается на лету (проверить), снимок области экрана; сравнение двух снимков | ПК |
| 7 | **Навыки** | `vic3-gui` в духе Impeccable: `init` пишет файл стиля интерфейса Vic3 из ванили, проходы `audit` / `polish` / `critique` с чек-листами; общий `vic3-sandbox`; `vic3-modding` — правила движка из «Правила работы с модами Victoria 3.md» | облако |
| 8 | **Сейвы и логи** | разбор сейва один раз в кеш, скрипты `save_*` / `scan_*` — запросы; общие разборы логов | облако + сейвы с ПК |
| 9 | **Рендер GUI** | `.gui` → PNG без игры: раскладка (`flowcontainer`, `hbox`/`vbox`, `layoutpolicy`, якоря, `scrollarea`), `.dds`, кадры и нарезка рамок, шрифты, заглушки вместо `[…]`; сверка со снимками игры через мост | облако + текстуры ванили |
| 10 | **Правила GUI для CWTools** (по желанию) | `.cwt` для виджетов, сгенерированные из корпуса ванильных `.gui`; отдать в `cwtools-vic3-config` | облако |

После каждого этапа — замер на трёх эталонных задачах; переезд скриптов из `vic3_mods` — только с тестом и
`--help`, старая копия удаляется в том же коммите.

## Правила для инструментов

- Docstring и `--help` — что делает и как вызвать, без истории (номера этапов и даты — в git).
- Вывод по умолчанию — короткий и с лимитом; длинное — в файл, на экран путь и сводка.
- Ничего не пишет вне указанных папок; `--check` у каждого генератора.
- Разовая проба этапа живёт в проекте, а не в репо инструментов; закончилась — в архив.

## Вопросы пользователю

1. Репо публичный или закрытый? От этого зависит, можно ли держать в нём выгрузки из игры (справочник ванили,
   типы данных) или они строятся только на месте.
2. Класть ли копию ванили в облако (для индекса, проверок и рендера без ПК) — и где её держать?
3. Имя репо и пакета.
4. CWTools (этап 5) — раньше, позже или параллельно?
