# ComPatch: LLWA + Victorian Century

**Game 1.13 (exe 1.13.11). Victorian Century (declares no version string); Locomotion: Land, Water, & Air (LLWA) 2.6.3.**

LLWA loads last in the target chain — after the megapack, Victorian Century, addon-VC, HC+GoB+MoH, and addon-HC. On records VC injects into, LLWA's `REPLACE:` (a bare full body) silently wipes the injection with no error and nothing in the log.

## What was being lost — and where the fix actually lives

Machine matrix: 6 shared keys, 0 shared paths (`tools/pair_matrix.py --pair "LLWA,VC"`). Split two ways, and **only the production_methods half is generated by this compatch:**

| keys | category | fixed here? |
| --- | --- | --- |
| `pm_no_passenger_trains`, `pm_steel_passenger_carriages`, `pm_wooden_passenger_carriages` | `common/production_methods` | **yes** — this compatch |
| `ai_strategy_great_reforms`, `ai_strategy_meiji_restoration`, `ai_strategy_tanzimat_reforms` | `common/ai_strategies` | **no — see `_llwa/llwa+kai done`** |

The three `ai_strategies` keys are the exact same three Kuromi's AI shares with LLWA (`LLWA.2`/plan) — LLWA's stale, pre-1.13 `03_political_strategies.txt` wipes an already-closed KAI × VC three-way merge (`_vc/kai+vc done`) on all three at once. Since fixing it needs KAI's file too, and needs the vanilla-restore file both the KAI pair and this pair depend on, that whole restoration — including VC's share of it — is generated by `tools/regen_llwa_kai.py` into `_llwa/llwa+kai done`. Writing it a second time here, referencing the same three keys from a different generator, would be exactly the "REPLACE_OR_CREATE from two compaches on one record" mine the project's rules warn about. **If you use this ComPatch, also install LLWA+KAI — that's where two of these six keys actually get fixed.**

## What was being lost (production_methods)

VC injects the identical thing into all three: `INJECT:building_modifiers = { unscaled = { building_job_attractiveness_mult = 2 } }` (`joi_methods.txt`). LLWA's `REPLACE:` on these three (`LLWA_rails.txt`) is a bare full body — on `pm_no_passenger_trains` there's no `building_modifiers` block at all; on the other two, `building_modifiers` exists (LLWA's own `workforce_scaled`/`level_scaled`) but never declares `unscaled`. Either way VC's addition is gone.

These three keys are **also** shared with TGR (`_llwa/llwa+tgr done`, 10-key pair). TGR's own numeric rebalance on the same fields is a genuine second design choice, not an absent key — per that compatch's rule (LLWA loads last, LLWA's numbers are what actually ends up in the game), it isn't restored anywhere, so there's nothing of TGR's left to add once VC's `unscaled` addition is accounted for, and this key is written exactly once — here, not in the TGR compatch.

## What's in this patch

One file, `common/production_methods/zz_llwa_vc_rails.txt`, three full `REPLACE_OR_CREATE:` records — LLWA's own body for each (including LLWA's own `pm_steel_passenger_carriages.unlocking_production_methods` addition, which neither TGR nor VC has, carried forward unchanged), with VC's `building_modifiers.unscaled` sub-block added back.

## How the merge is made

`tools/regen_llwa_vc.py`. Reads LLWA's and VC's current `LLWA_rails.txt` / `joi_methods.txt` live, asserts VC's extracted `unscaled` content is still exactly `building_job_attractiveness_mult = 2` (fails loudly on drift), and splices it into LLWA's own body — creating the `building_modifiers` block from scratch where LLWA doesn't have one (`pm_no_passenger_trains`) rather than assuming it exists.

## Notes

* **Maintenance.** Everything is generated by `tools/regen_llwa_vc.py`. Re-run after either mod updates; `--check` reports drift without writing.
* Victorian Century declares neither `version` nor a workshop `id`, so it can't be named in `relationships` — only in the description and `tested_with`, same as everywhere else VC appears in this set.
